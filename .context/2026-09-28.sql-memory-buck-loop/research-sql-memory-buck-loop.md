# Exploration: SQL memory in buck-loop

## Findings

1. **Store exists; loop integration does not.** `extensions/index.ts:14,31` wires `sql_memory`; `extensions/sql-memory/index.ts:7-12,21-64` exposes `{op:"sql",statement}` for one gated `SELECT`/`INSERT`/`UPDATE` or `{op:"migrate",destructive?}`. `SQL_MEMORY_URL` gates registration. The DML path uses `BEGIN`, local public search path, rollback on failure, and returns `{rows,rowCount}` or `{error:true,message}`. The live read-only `sql_memory` call `SELECT version FROM schema_migrations ORDER BY version` returned `[{version:"001"}]`, `rowCount:1` in this session. No skill currently mentions `sql_memory` (`grep skills/`).
2. **Schema and identity.** `migrations/001_initial_schema.sql:18-60,92-125` has `users.email` (git email), `projects.origin_url` (git remote or common-dir fallback), memory category, explicit `seq`, branch+SHA pair, `context jsonb`, current/superseded fields, generated full-text search, and immutable content/provenance trigger. `docs/sql-memory.md:12-14,30-59` defines project-wide/all-branch recall with branch as provenance; no merge-close. `memory_embeddings` are optional and not a prerequisite to text recall. PostgreSQL 18 plus pgvector required for migration 001.
3. **Tool shape gaps.** The SQL tool accepts a statement string but no bind parameters (`index.ts:7-12,39`), although the gate permits `$1` placeholders (`sql-gate.test.ts:5-12`); dynamic body/email/origin/subject interpolation is unsafe. The gate rejects `DO` tokens and only allows one statement, so generic `ON CONFLICT DO NOTHING` upserts and multistatement saves cannot be assumed (`sql-gate.ts:13-30,145-231`). `db.ts:1` currently statically imports `pg` (an existing unstaged user change), despite previous Phase 2 notes claiming lazy module load; the pool itself is created on first use (`db.ts:4-12`). Never prescribe direct DB writes in skills.
4. **Loop boundary.** `extensions/buck-loop/loop.ts:438-467` runs one nested skill then rescans disk; the child is isolated by `run-step.ts:134-144,393-415` (`restrictToolNames:true`, `disableExtensionDiscovery:true`, no MCP/LSP, in-memory transcript). No child has `sql_memory` today. `scan.ts:444-459` confirms saving only when `.context/memory/` changed. `machine.ts:312-346` permits a Jev `advance` from an *ambiguous* saving postcondition, so simply writing SQL (or a failed SQL tool result) could still commit without a confirmed memory write. Run state is a local projection (`persist.ts`), artifacts win over model prose; `b-commit` has only `read,bash` tools. A SQL save receipt/pointer and a fail-closed save transition must be coordinated.
5. **Skill boundary.** `skills/b-save/SKILL.md:32-63,84-100` writes a full `.context/memory/*.md`, index and optional OMP retain; `skills/b-build/SKILL.md:292-313` and `skills/b-iterate/SKILL.md:28-52` rewrite those files at natural stops; `skills/b-review/SKILL.md:456-460` checks the index. `b-phase` delegates to `b-save`; thin prompts/commands do not own behavior. `b-save-improved` is a separate deterministic command, not invoked by `/buck-loop`'s `NestedSkill` list (`run-step.ts:56-65`). Global/project bootstrap and subject resolution (`skills/_shared/subject-resolution.md:17-23`) also assume portable session memory files.
6. **Jev is already limited.** `extensions/buck-loop/choice.ts:140-166` asks native Jev only when the machine presents ≥2 legal continuations after ambiguous scan/review; fallback is choice-stage model then block, audited under `transition-audits/`. `extensions/jev-tool/index.ts` is a generic TypeSafe `systemOne` tool. Semantic memory selection can use closed-set Jev on a bounded SQL shortlist, but Jev cannot write SQL, memories, category labels or summaries. Deterministic identity, scope, freshness, SQL safety, deduplication key, and write receipt should stay outside judgment.
7. **Brainstorm precedence.** Today's `brainstorm-postgres-agent-memory.md:9-16,40-46` sketched Jev store/merge/reject, value scoring, shortlist `noul`, episodes, and `turn_end` capture. The later completed grill and plan explicitly ratified Q1 SQL replaces new `.context/memory` bodies; Q4 no *required* Jev gate or `turn_end` writer; Q12/13 branch provenance without merge-close and cross-branch recall (`grill-session-postgres-agent-memory.md:32-50`, `plan-postgres-agent-memory.md:24-53`). Future Jev may be opt-in on real ambiguity, not an obligatory capture gate. The older external-context-store brainstorm is a distinct KV+pointer hydration concept for the entire `.context` tree, not the SQL memory table (`.context/2026-08-27.external-context-store/brainstorm-external-context-store.md:12-22,41-49`).
8. **Actual OMP child tool admission.** Official OMP SDK docs at `can1357/oh-my-pi@33f887a` say `toolNames` alone is not an allowlist; restricted children cannot gain extension-contributed tools by discovery. SDK `customTools` require `allowRestrictedCustomTools:true` *and* their name in `toolNames`. The plan should reuse the SQL tool implementation via a restricted custom-tool adapter, not enable all extension discovery. Verify shape against the installed OMP runtime; this repo imports the Pi package in TypeScript. Source ledger: `research/sources-omp-child-tools.md`.

## Design constraints for the plan

- SQL configured: new reusable memory records live only in Postgres (Q1); replace new `.context/memory/` files rather than hiding a second record there. Use a metadata-only save receipt under the active subject as control-plane evidence; change the current cross-reference, status, subject-resolution, and commit contracts together. SQL absent: retain today's portable file-based save path and report shared recall/store unavailable. This research session still follows the currently installed mandatory file contract.
- Retrieval: derive project identity deterministically; SQL shortlist must filter `invalid_at IS NULL`, bound rows and content, show branch/SHA, and prefer `plaintext_to_tsquery` on bound user input. Query before relevant child work; never import entire table or override plan/phase authority. Missing/failed DB must be visible, not silently interpreted as empty memory.
- Writes: user/agent chooses candidate facts from actual work; only `b-save` or explicit tool use writes. Store with immutable-body semantics, category from active taxonomy, stable source identity for retry, `INSERT ... RETURNING id`, and SQL read-back before writing a subject-scoped receipt. Supersede via new row then `invalid_at`/`superseded_by` on the old ID; do not silently rewrite. No `turn_end` hook or mandatory Jev decision.
- Least privilege: recall stages execute only DB read-only transactions, while save may write necessary memory/user/project rows but not `migrate` or arbitrary user-weight mutations. `b-commit` gets no SQL tool. Reuse the existing gate/executor instead of forking SQL parsing. The custom-tool pool lifetime and failure reporting need a concrete implementation design.
- Safety: a rejected/failed SQL save must not be rendered as a successful nested session or Jev-advanceable ambiguous postcondition. Successful SQL save plus a matching subject receipt, or an explicit no-fact receipt after SQL connectivity, is the only automatic route to commit in configured mode. Preserve local file fallback only when SQL is not configured.
- Jev belongs in the parent loop for optional, bounded shortlist relevance decisions: validate IDs against SQL candidates and pass only admitted IDs to children. No ambient Jev tool in restricted children and no mandatory save classification. The existing continuation judgment must not bypass failed persistence.
- Q14 makes all user memories shared immediately, with no RLS. Default project filtering is a recall policy, not an authorization boundary; deliberate cross-project reads remain possible.
