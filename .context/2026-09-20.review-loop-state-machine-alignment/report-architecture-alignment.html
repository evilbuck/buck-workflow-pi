The review loop, re-decided by a pure evaluator

Comparing extensions/code-review-iteration/loop.ts as it stands today — an imperative supervisor whose decisions are scattered across control flow — with a proposed alignment onto the domain-neutral rule evaluator in extensions/state-machine.ts, the same seam /buck-loop already runs on.

Date 2026-09-20 Subject 2026-09-20.review-loop-state-machine-alignment Status draft — for decision Surface extensions/code-review-iteration/ (16 files, ~4,000 LOC incl. tests)

Recommendation

Align the decision layer only. Introduce extensions/code-review-iteration/machine.ts: an explicit ten-state review machine (five work states, five terminals) whose rules are pure predicates over a facts projection. loop.ts keeps every effect — git, model sessions, pass artifacts, RunState persistence — but stops deciding with control flow; it asks the machine, executes the returned output, and rescans facts. No schema bump, no new orchestration runtime, no behavior change: the 24-scenario integration suite is the migration contract.

Decisions centralized: 6 sites → 1 rule table Resume unified: one projection, no special case Effects, artifacts & API untouched Evaluator choice/send machinery: intentionally unused here
01

Current architecture — the implicit machine

loop.ts · 729 lines

Today's review loop is a well-behaved imperative supervisor with an invisible state graph. It works: bounded passes, immutable artifacts, resumable runs, five terminal statuses. But the graph exists only as the shape of the control flow — there is no place to read it, no place to test it in isolation, and no single answer to "what state is this run in?"

Figure 1 — runReviewLoop today: decisions (D) buried in orchestration
Current · today

Traits of the imperative design

  • State is implicit. "Where am I?" = RunState.status + pass + which pass artifacts exist, re-derived ad hoc at each site.
  • Decisions live in control flow. Seven decision points (D1–D7) are spread across five functions; none is unit-testable without the git/model harness.
  • Resume is a special case. resumeIncompleteFixer re-implements a slice of the pass logic by reading review.json/fixer.json.
  • Terminal classification is scattered. Five statuses are written from nine call sites; the reason strings are built inline.
  • Sequencing and I/O are fused. Deciding the next step and performing git/session effects happen in the same function bodies.
  • Testing is integration-only. The 630-line loop.test.ts exercises every decision through real temp-repo clones.
Proposed · aligned

Traits over the pure evaluator

  • State is explicit. A nine-state ReviewState union; stateOf(facts) is the single projection from RunState + pass artifacts.
  • Decisions live in one rule table. Named, grep-able automatic rules in machine.ts; pure predicates, truth-table testable.
  • Resume is the same code. Resuming is projecting facts — the forward path and recovery path share one stateOf.
  • Terminals are declared once. Five terminal states; outputs carry { status, reason } so the supervisor has one write path.
  • Effects stay in the supervisor. loop.ts interprets opaque outputs; the evaluator cannot touch git, models, or the clock.
  • Two test tiers. Pure truth-table tests for every edge + the unchanged 24-scenario integration suite as the behavior contract.
02

The evaluator contract being aligned to

state-machine.ts · 441 lines · proven in production

extensions/state-machine.ts is a synchronous, pure rule evaluator extracted from /buck-loop and already load-bearing: extensions/buck-loop/machine.ts:542 defines buckMachine over it. It owns exactly three operations and refuses every illegal situation with a typed failure.

OperationSemanticsRelevance to the review loop
advance(facts) Exactly one enabled automatic rule → TransitionDecision; otherwise the legal choices set; otherwise NO_ROUTE. The whole migration. Every current decision point D1–D6 becomes an automatic rule with a mutually-exclusive guard.
choose(facts, c) Revalidates a returned choice against current facts; stale choices rejected (ILLEGAL_CHOICE), never replayed. Unused here — by design. The review loop has no operator-choice surface; pretending otherwise would manufacture scope.
send(facts, e) External event matched by key; exactly one enabled rule must pass. Deferred. Cancellation today is exception typing at the supervisor boundary; routing it through send is a listed alternative, not the recommendation.
§

Why this seam exists at all

The evaluator's own header states the division of labor the migration must respect: "Consumers own facts, states, events, choices, and opaque outputs. This module only selects one valid route." Thirteen MachineFailure codes (AMBIGUOUS_AUTOMATIC, NO_ROUTE, INVALID_TARGET, …) make every ambiguity a loud, typed error — the same fail-closed posture the review loop already applies to reviewer payloads and checks.

Guarantee (state-machine.ts)What it buys the review loop
Pure & synchronous — no I/O, clock, promises (lines 1–7, 165–199)Rules are truth-table testable in microseconds; no mocking of git or sessions to test a decision.
Ambiguity is an error, not a priority orderThe seven today-scattered decisions must be written as mutually exclusive guards — precedence becomes visible in the rule table, not buried in if ordering.
Opaque Output genericOutputs carry { effect, status?, reason }; the evaluator never learns what a "fixer" is.
Terminal states refuse advanceclean/blocked/exhausted/failed/cancelled become states the machine structurally cannot fall out of.
03

Proposed alignment — the explicit machine

+1 module · machine.ts ~220 LOC

One new module, extensions/code-review-iteration/machine.ts, declares the review lifecycle over defineMachine. loop.ts becomes a thinner supervisor: project facts → advance → execute output → persist → rescan.

Figure 2 — proposed ReviewState graph (automatic rules only; terminals solid)

The shape of the new facts projection

// extensions/code-review-iteration/machine.ts (sketch)
export type ReviewState =
  | "initializing" | "preparingBase" | "reviewing" | "triaging" | "fixing"
  | "clean" | "blocked" | "exhausted" | "failed" | "cancelled";

export interface ReviewFacts {
  state: ReviewState;          // derived by stateOf() — never persisted
  pass: number; maxPasses: number;
  catalogOk: boolean;
  baseReady: boolean;           // RunState.base_commit !== null
  baseError?: string;           // detect/fetch/rebase failure captured by supervisor
  review?: { blocking: number } // pass NN/review.json   — present ⇒ review parsed
  reviewError?: string;        // payload contract / session failure
  fixer?:  { checksPassed: boolean }; // pass NN/fixer.json — present ⇒ fixer ran
}

export type ReviewOutput =
  | { effect: "run-catalog-preflight" } | { effect: "prepare-base" }
  | { effect: "run-reviewer-pass" }     | { effect: "triage-findings" }
  | { effect: "run-fixer-pass" }
  | { effect: "terminal"; status: RunStatus; reason: string };

export const reviewMachine = defineMachine<ReviewState, ReviewFacts, never, never, ReviewOutput>({
  stateOf: (f) => f.state,
  choiceKey: unsupported,      // no choice surface — compile-time never
  eventKey:  unsupported,
  states: {
    "triaging": {
      automatic: [
        { id: "triage-clean",     when: zeroBlocking,        target: "clean",    output: terminal("clean", …) },
        { id: "triage-to-fixer",  when: hasBlocking,         target: "fixing",   output: () => ({ effect: "run-fixer-pass" }) },
        { id: "triage-uncomputable", when: hardnessMissing, target: "failed",   output: terminal("failed", …) },
      ],
    },
    "fixing": {
      automatic: [
        { id: "fixer-continue",   when: checksPassedAndPassesRemain, target: "reviewing", … },
        { id: "passes-exhausted", when: checksPassedAndPassesSpent,  target: "exhausted", … },
        { id: "fixer-blocked",    when: checksFailed,               target: "blocked",  … },
      ],
    },
    // … initializing / preparingBase / reviewing likewise; five terminal: { terminal: true }
  },
});
⇄

The supervisor tick after migration

stateOf(project(runDir, state)) → reviewMachine.advance(facts) → interpret output.effect with today's exact functions (prepareBaseAndCheckpoint, runReviewerPass, runFixerPass, …) → write artifacts/RunState → loop. A MachineFailure — which should be unreachable for a well-formed projection — is converted to failed with the code and context in the reason, mirroring how /buck-loop durably blocks on machine failure.

✳

Behavioral subtlety preserved by design

Today the fixer runs even after the final review pass (blocking findings on pass N = max still trigger runFixerForPass); exhausted is only declared when the next review cannot start. The proposed graph encodes exactly this: triage-to-fixer is unconditional on blocking, and exhaustion is decided in fixing by comparing pass to maxPasses. A naive "review → exhausted" shortcut would be a silent behavior change — the truth-table tests pin it.

07

Alternatives considered

and why not (yet)
Recommended

Decision layer only

machine.ts + thin supervisor. Smallest change that removes the actual problem (implicit, scattered, untestable decisions). Keeps the evaluator's no-runtime promise. ~1 module, ~220 LOC + tests.

Rejected

Full buck-loop-shaped port

Split into scan/persist/run-step modules, re-derive facts from disk each tick, generic effect loop. ~3× the work, re-litigates a loop that already works, and walks straight into the "another orchestration framework" failure mode the state-machine plan warned against.

Deferred

Operator events via send()

Route cancellation through machine events instead of LoopCancelledError at the boundary. Cleaner typing, but touches the cancel path's UX and tests for marginal gain. Natural follow-up once the decision layer lands.

⚠

Persisted machine state — rejected

Adding machine_state to RunState (schema bump → 2) would orphan in-flight schema-1 runs and force validateResume migration handling — all to store what stateOf derives for free from fields and artifacts that are already durable. Derivation also keeps resume honest: the state on disk can never disagree with the artifacts on disk.

Risks & standing invariants

what could go wrong, and the fences
RiskMitigation / invariant
Silent behavior change The 24 integration scenarios are the frozen contract; they must pass unmodified. The §05 behavior map doubles as the truth-table test checklist. The fixer-on-final-pass subtlety gets an explicit pinning test.
Framework creep Standing rule from the prior extraction plan: the reusable seam is the pure decision evaluator, not an asynchronous orchestration runtime. No effects-in-machine, no persistence hooks, no async supervisor — outputs stay opaque data.
False reuse / ceremony Honest accounting: this loop uses only advance(). The win is decision centralization + a shared, tested vocabulary with buckMachine — not feature utilization. If that trade feels thin, the full-port alternative is strictly worse, not a better deal.
Guard drift between rules and writes Because state is derived and outputs carry the single {status, reason} write, the machine table and persisted state cannot disagree; the supervisor loses its independent early-return paths.
Projection cost stateOf reads at most two small JSON files already being read today (resume peek); no new scanning layer, no stat storms.
