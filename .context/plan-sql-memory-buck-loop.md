# Plan: SQL memory in buck-loop

## User Goal

Engineers share one remote PostgreSQL memory store across all projects: any OMP agent can store and recall memories scoped by project and git branch, ranked by author skill and value, with order and context preserved — replacing `.context/memory/` for new memories. For `/buck-loop`, this means isolated work stages can recall shared context and save durable new facts without a parallel Markdown body store. (Ratified goal: `.context/2026-09-28.postgres-agent-memory/plan-postgres-agent-memory.md:24-26`.)

## Goal

Make the existing PostgreSQL memory tool usable inside isolated Buck work sessions and make SQL-backed saves observable to the supervisor. When `SQL_MEMORY_URL` is configured, SQL is the source of new reusable memory bodies; a metadata-only receipt under the active subject records SQL IDs and save-attempt state for review, resume, and commit. Do not create a new `.context/memory/` file in SQL mode. Without SQL configuration, the existing portable file-based behavior remains available. Do not introduce a mandatory Jev gate or turn-end writer.

## Context used / decisions

- Current tool/schema: `extensions/sql-memory/`, `migrations/001_initial_schema.sql`, `docs/sql-memory.md`. Earlier Postgres-agent-memory phases 1–3 already deliver this store; do **not** rebuild it.
- Today's `brainstorm-postgres-agent-memory.md` explored Jev store/merge/reject, value scoring, and shortlist relevance. The **later ratified** `grill-session-postgres-agent-memory.md:32-50` and `plan-postgres-agent-memory.md:24-53` decide SQL **replaces new `.context/memory/` records** (Q1), no required Jev memory gate or `turn_end` writer (Q4), branch as provenance (Q12), and all-branch project recall (Q13). Preserve only control-plane receipts under the active subject, not new memory files.
- Current bootstrap and `skills/b-save` still require full portable memory files; `scan.ts:458` and `machine.ts:339-343` allow file-only confirmation/ambiguous save advance. `skills/_shared/subject-resolution.md:17-23` reads a `current-session.json` memory pointer that `b-save-improved` reports stale. Change these coupled contracts together. (The existing historical memory files remain readable; do not migrate them.)
- OMP SDK `can1357/oh-my-pi@33f887a` supports restricted `customTools` only with `allowRestrictedCustomTools:true` and a matching `toolNames` entry; ambient extension discovery cannot safely grant `sql_memory` to children. Source ledger in `research/sources-omp-child-tools.md`. Prove this on the deployed OMP fork before building on the seam.
- `.context/2026-08-27.external-context-store/brainstorm-external-context-store.md` is a separate KV+git-pointer hydration design for the entire context tree, not this memory integration.

## Scope / non-goals

**In:** OMP `/buck-loop` nested work stages, portable Buck skills they load, the alternative `b-save-improved` entry point so new memory is not written to a competing body store, the installable/project agent bootstrap, and memory-facing docs. `sql_memory` remains the only PostgreSQL access surface; skill markdown never opens a DB connection.

**Out:** import of historical `.context/memory/*.md`, migrating plans/specs/backlog to PostgreSQL (external phase 2), `turn_end`/`message_end` auto-writers, arbitrary new taxonomy labels, summary generation, embeddings/HNSW automation, modifying user skill weights in loop children, replacing the current Jev continuation engine, changes to Pi/Codex tool loading beyond portable file fallback. No automatic migration call from the loop.

## Proposed flow

1. **Admission:** In SQL-configured OMP loop stages, inject a scoped adapter of the existing `sqlMemoryTool` as SDK `customTools` with `allowRestrictedCustomTools:true`, its name in `toolNames`, and `restrictToolNames:true`; prove the installed OMP contract first. Do not enable extension discovery or MCP. Extend the shared SQL gate/executor with role policy: build/review/iterate/docs/howto can recall only in DB read-only transactions; save can INSERT/UPDATE only necessary memory/user/project rows, not `migrate` or skill-weight mutation. `b-commit` gets no SQL. Reuse a bounded pool with explicit lifetime handling. A configured OMP loop blocks on tool/DB failure, not file fallback. Portable skills use SQL only when the tool is callable; other harnesses retain the file path and report shared SQL unavailable.
2. **Recall:** A portable shared instruction used by relevant skills derives the project key from git origin (redacting URL credentials), or absolute common git dir; branch and full commit SHA are provenance, **not** recall filters. Fetch a bounded active (`invalid_at IS NULL`) shortlist across all project branches with ID, body, category, origin/branch/SHA, and SQL-side text/author-value ranking. Bind inputs (`plaintext_to_tsquery` for free text), bound rows/content, never make the retrieved text an instruction, and defer to current plan/phase files if a memory conflicts. Missing DB/config is visibly distinct from zero matching memories. Do not load an entire project memory table into a child prompt.
3. **Jev (only where ambiguous):** The parent loop may fetch a small active-project SQL shortlist before a nested stage and use native `runJev` for closed-set `noul` relevance judgments over existing candidate IDs, then pass only validated IDs/provenance to the child. Child agents retain scoped SQL recall; they do not gain ambient Jev or model-generated SQL. Keep SQL ranking/order for deterministic ties. No Jev call for obvious/no-candidate cases. Jev missing/failure retains the deterministic shortlist, never invents IDs or advances a failed save. A future write-side `store_new | supersede_existing | skip` choice needs a bounded proposal/duplicate-candidate artifact; do not add a mandatory save gate now. Existing loop continuation Jev stays as-is except it cannot override an unverified SQL save.
4. **Save:** `b-save` selects self-contained decisions/conventions/outcomes from actual work, not every turn. With bound `sql_memory` statements, ensure user/project identity, look up a stable source key in `memories.context` before writing (single-run retry safety), and `INSERT ... RETURNING id` with git email, project ID, branch+SHA pair (or both NULL), active category, explicit per-session `seq`, and subject/phase/source context. A correction inserts a successor then updates only `invalid_at`/`superseded_by` on the old row; never update immutable content. After same-project read-back, write a metadata-only `.context/<subject>/sql-memory-receipts/<run-id>-<attempt>.json` with project key, attempt ID, SQL IDs and outcome; no new `.context/memory/` file or index entry in SQL mode. A legitimate no-reusable-facts outcome uses an explicit empty-ID receipt **after** a successful SQL connectivity probe; distinguish it from a failed DB write. Update plan/spec cross-references to SQL receipt/IDs rather than `memory:` Markdown paths, and keep backlog/phase/lifecycle duties.
5. **Postcondition:** The supervisor generates the save-attempt ID before launching `b-save`, then in SQL mode confirms the matching subject receipt and same-project SQL IDs by read-back before `saving → committing`. The changed-file list or child last sentence alone is insufficient; a stale receipt cannot satisfy a new attempt. `{error:true}`, missing row, or DB outage blocks with an operator-visible reason. Remove the ambiguous `saving` Jev `advance` route for unverified SQL mode; retry or block, never vote past persistence. On `--resume`, reconcile receipt and rows before commit; keep phase/plan artifacts authoritative and do not persist the database URL. File mode preserves existing full memory-file contract, except an unconfirmed save must not be treated as proof.

## Acceptance criteria

- [x] With SQL configured, an isolated `/buck-loop` child executes a real `sql_memory` SELECT, then an explicit save INSERT/read-back; the tool is unavailable to `b-commit` and has no migration permission in any child.
- [x] Default recall is project-scoped and includes active memories from other branches with provenance and relevance ordering; invalidated memories are excluded. Cross-project reads remain an intentional capability of this shared, no-RLS store (Q14), not a new security guarantee. Quotes in user inputs and body text remain data via bound parameters.
- [x] Optional parent Jev relevance uses only legal shortlist IDs; a bad verdict cannot add an ID. No Jev call is required for an ordinary store/recall, no `turn_end` writer runs, and Jev outages cannot advance a failed save.
- [x] SQL-backed saves leave a subject-scoped, metadata-only receipt, **no new `.context/memory/` file or index entry**. Resume and commit require the matching attempt and same-project SQL rows, or an explicit no-fact receipt after SQL connectivity succeeds; DB error or missing row blocks visibly. Replaying a save in one run does not duplicate it.
- [x] With no `SQL_MEMORY_URL`, Buck's current portable file save/recall remains functional and reports no shared store. Non-OMP harnesses without a callable `sql_memory` tool retain the file path even if an environment variable exists, with a visible availability note; a configured OMP loop never silently downgrades after SQL failure. Historical memory files remain readable.
- [x] `b-save-improved`, `b-build`/`b-iterate`, `b-review`, subject resolution, and bootstrap cannot silently create or require a competing full `.context/memory` body in SQL mode. Historical memory files remain readable without migration; non-OMP/file mode retains its existing behavior.

## Risks / decisions

- **Policy cutover:** ratified SQL replacement conflicts with the current mandatory `.context/memory` bootstrap. Change bootstrap, skills, and supervisor together: SQL mode emits a subject-scoped receipt only, while existing full memory files remain for legacy/unconfigured use. The receipt is not an offline copy of facts; the SQL database must be reachable to fetch their bodies. Until the cutover ships, this planning session follows the current file contract.
- **Restricted SDK version:** the repo typechecks against `@mariozechner/pi-coding-agent` while deployed OMP has different custom-tool admission. A live OMP child proof is a hard prerequisite; do not relax `restrictToolNames` or enable ambient discovery to work around a mismatch.
- **Safety/identity:** `sql_memory` currently accepts raw statements only; add parameter binding before any dynamic writes. Reuse git identity carefully: `resolveGitIdentity` falls back to `cwd` after broad Git failure (`extensions/token-attribution/git-identity.ts:49-78`), which is not the locked common-dir fallback. Report failure rather than assigning memories to an accidental project.
- **Concurrency:** an application-level source-key lookup prevents single-run retry duplication, not simultaneous writers with the same key. If cross-worker exactly-once is required, add a database uniqueness design as a deliberate migration; do not claim it from the current schema.
- **Shared visibility:** The current schema has no row-level security (Q14). Project filtering is a default recall behavior, not an isolation boundary; do not claim cross-project access is blocked without a separate authorization design.
