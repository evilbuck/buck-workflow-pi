User goal

SQL-mode /buck-loop save checkpoints verify deterministically. A child that persisted real memory rows and wrote a real receipt must verify and commit — never fail its postcondition over an identity field it was never given.

The fix — four one-line moves

1

Dictate the subject

Insert subject: ${attempt.subject} after the runId line. Field order mirrors SaveAttempt. Nothing else in the directive changes.

extensions/buck-loop/sql-save.ts
2

Pin the contract in the skill

Add subject to the “directive names these values — use them exactly” list; the receipt’s subject field and the op: "remember" parameter are that value, copied exactly.

skills/b-save/SKILL.md
3

Recopy the bundled skill

Byte-identical copy — scripts/codex-plugin.test.ts enforces the canonical mirror and fails otherwise.

plugins/buck-workflow/skills/b-save/SKILL.md
4

Regression-test the identity

Assert the directive carries the complete receipt identity — subject: alongside the existing attemptId / runId / project / receipt assertions.

07

Risks & recovery

Residual mistranscription

A model could still mistype a dictated field. Accepted: dictation is exactly how attemptId / runId / project stayed correct in every observed receipt — the incident’s only failure was the undictated field.

Skill-copy drift

The two b-save copies can diverge. Mitigated: recopy in the same change; the Codex mirror test fails the suite otherwise.

Recovering the blocked run · 2026-09-30.buck-loop-tui-preview

After the fix, resume the subject — the attempt is reused and the child re-runs the save stage. Caveat to check at resume: if the original remember call passed the inflated subject, the retry inserts a second row under a different source key — supersede the duplicate via previousId.
