01 / The problem

Promises are not enforcement.

Buck Workflow is a toolkit of agent skills, mirrored command prompts, installers, and quality guardrails. Today, many important contracts live only in prose or convention—the exact place where a copy can drift, an agent can forget, or a CI run can look green without checking the intended thing.

Trust moves from “someone remembers” to “the machine refuses.”
01 · CATALOG

Metadata can quietly break

There are 64 direct skills; exactly one has no YAML frontmatter: skills/code-review/SKILL.md. Its own pr-ref.test.ts still passes 7/7 in 96ms—passing tests did not verify the catalog promise.

02 · BUNDLE

Copies are already drifting

The physical, self-contained Codex bundle has 30 skills and 8 live canonical-copy differences. No parity check turns that drift into an immediate failure.

03 · MIRROR

Mirrors need a decision

commands/ has 43 entries: 35 symlinks and 8 physical files. Four physical twins diverge from prompts/; four have no prompt counterpart.

04 · SECURITY

A real scanner is unwired

The 696-line security-audit.sh scans secrets, PII, profanity, and history, but nothing invokes it in the repository.

05 · GATES

The contract is only prose

guardrails.json v2 has no gates key and no required/advisory/disabled states. Its six-gate verdict exists only in the b-guardrails-check skill narrative.

06 · RUNNER

Interpretation is the runtime

skills/b-guardrails-check/ contains only documentation—no scripts directory or executable. An AI agent computes the verdict by reading instructions.

YAML frontmatter — a small structured header at the top of a skill file; tooling can reliably read its name and description.

Symlink / physical file — a symlink points to one source of truth; a physical file is a separate copy that can diverge.

Quality gate — a check that must produce a clear pass/fail decision before work proceeds.

Ratchet — a baseline that may tighten but must not quietly get worse.

Pre-push hook — a local Git action that runs just before a push; it can stop unsafe changes.

Hermetic test — a test in a controlled environment, proving a package works without accidental help from the developer’s machine.

03 / Workstreams

Five routes from convention to refusal.

Each workstream names a current failure mode, a bounded planned change, and the observable reason it is worth doing.

W1 P0

Skill catalog integrity

ProblemOne skill lacks frontmatter; the self-contained bundle already has eight live copy differences.
Planned changeFix that header; add a Vitest test for every direct skill’s valid frontmatter (unique name = directory, nonempty description); declare inventory and recursively byte-compare bundle copies, allowing only the two Codex-only skills: b-build-hard and b-commit.
BenefitYou can trust the catalog and bundle because a changed or missing contract becomes a red test—not a later surprise.
W2 P0/P1

Distribution & install integrity

ProblemCommand mirrors contain physical twins and special entries; an installation can appear fine only because a workstation PATH happens to help it.
Planned changeFinish the mirror decision, then test from prompts/: every prompt has exactly one command symlink, with no physical twins except documented exceptions. Add a hermetic smoke test: npm pack → temp-prefix install → bash -lc 'buck-workflow --list'.
BenefitMirror drift cannot silently return, and the published CLI is proven discoverable in a real login shell.
W3 P1

Guardrail enforcement

ProblemCI has one job—npm ci, then npm test—and no guardrail runner, Lizard, or diff-cover provisioning. Verdict rules are prose.
Planned changeAdd explicit required/advisory/disabled states per gate. Extract verdict computation into one deterministic check.mjs used by both the skill and PR CI. Required failures exit nonzero; ratchets remain. Patch coverage begins advisory and is promoted only after green clean CI.
Benefit“Tests pass before you claim done” stops depending on an agent’s interpretation; the same executable decides locally and in CI.
W4 P2

Opt-in pre-push security hook

ProblemA real 696-line scanner is unused, while the installer’s --verify mode knows nothing about hooks.
Planned changeProvide hooks install/status/remove, plus a managed pre-push launcher for the audit. It chains existing hooks or safely refuses; it never silently overwrites core.hooksPath.
BenefitDetectable secrets can block a push, while engineers keep control of their existing hook tooling and latency trade-offs.
W5 P2

Docs & close-out

ProblemNew enforcement is only useful when users understand its contracts and status.
Planned changeSync living docs, then run b-review → b-docs → b-save → b-commit.
BenefitThe documented workflow matches the enforced workflow, and close-out is reviewed and recorded.

05 / Deliberate limits

What this plan will not do.

Boundaries protect the plan from replacing one vague promise with an overgrown, risky change.

No bundle symlink

It would break the Codex bundle’s standalone, self-contained packaging.

No stale counts as contracts

The comparison report’s old numbers do not become rules; tests derive from measured structure.

No unrelated debt cleanup

Existing coverage and complexity debt is not fixed inside this enforcement plan.

No automatic hook installation

Package installation will not alter local Git hooks without an explicit opt-in.

No revival of b-flow

The dead extension is outside this plan’s integrity and enforcement scope.
