# Session: 2026-09-11 — Unified live activity for extensions

## User Goal

When an extension makes LLM calls and starts doing work, I see an animated status indicator and a small live window of what the LLM is doing in the main TUI content area, consistently across all extensions.

## What happened

- User asked (via "/b-plan") for animated spinner next to status + a small TUI window showing what the model is working on for long-running operations such as rebase conflict resolution. User clarified the design must apply across extensions, not just `b-pr-improved`, and should be modular.
- Walked the existing deterministic-progress subject and confirmed `extensions/command-progress.ts` is the canonical seam but mixes UI lifecycle with subprocess helpers and lacks animation/event-stream support.
- Verified the OMP SDK surface: `ExtensionUIContext.setStatus()` and `setWidget()` are the only documented non-modal footer/above-editor surfaces; `AgentSession.subscribe()` exposes `message_update` text deltas, tool lifecycle, retries, and completion events. Sources cited in the plan.
- Designed one deep `extensions/extension-activity.ts` module owning activity lifecycle, animation, bounded rendering, sanitizer, throttle, feature detection, and idempotent cleanup.
- Designed normalized `ActivityEvent` union inside `runOmpModelSession()` so the UI module never parses SDK events directly.
- Decided to extract subprocess helpers from `command-progress.ts` into `extensions/subprocess.ts`, leaving no alias, so the package keeps a single source of truth for UI progress and subprocess capture.
- Wrote plan `plan-extension-activity-progress.md` with eight implementation steps, 13 acceptance criteria, automation + OMP TUI verification, and risks (render pressure, terminal injection, wrong surface, UI pollution, silent model calls, cleanup leaks, cross-runtime variance, legacy source confusion).
- Ran `/b-phase` to produce a 4-phase execution map; Phase 1 (subprocess extraction) is `easy`, Phases 2-4 are `medium`.

## Decision

- One reusable activity module at the command/UI seam. No process-global singleton.
- Footer spinner through `setStatus(key, frame+label)`; live window through `setWidget(key, lines, { placement: "aboveEditor" })` with a 9-line cap (1 header + 8 activity lines) under OMP's documented 10-line string-widget limit.
- Normalize OMP `AgentSessionEvent` values inside `runOmpModelSession()` before forwarding to the activity handle.
- Tool arguments are untrusted; only allowlisted display metadata (e.g., repo-relative file path) is shown. No raw prompts, edit contents, command environments, or tool results.
- Bounded coalescing, ANSI/control stripping, and a fixed widget redraw rate.
- Extract subprocess helpers into `extensions/subprocess.ts`; delete `extensions/command-progress.ts` after clean cutover.
- Migrate `b-pr-improved`, `b-commit-improved`, `b-save-improved`, and `b-kamal-release` to the new handle; deprecate `b-flow` and `b-grill-auto` are explicitly NOT retrofit targets.
