01

Prepare your kitchen

This recipe uses the evaluator shipped in the Buck Workflow source repository. It is not an import from a globally installed CLI package. You need basic TypeScript familiarity, a text editor, and a Bash-compatible terminal on Linux, macOS, or Windows through WSL.

  1. Install Git and Node.js 22 or newer. Node includes npm. If you use WSL, install them inside WSL. Reopen your terminal after installation.
  2. Check that these commands print version numbers. Your Node version must be v22 or newer.

02

Sketch the workflow

Our article moves through four states. Submitting is an external event; reviewing offers a decision; an approved article is published automatically. Publication here means writing a local text file, not posting to a website.

draftWait for SUBMIT
reviewOffer approve / reject
approvedPrepare the file write
publishedTerminal: stop

Alternative route: choosing reject in review returns the article to draft.

IngredientWhat it means here
StateOne of the four names above. A TypeScript union prevents spelling a different state by accident.
FactsThe current state, title, body, and reviewer availability. The caller supplies a fresh snapshot.
ChoiceAn option to select: approve or reject. The machine declares which options are legal.
EventA signal pushed into the machine: SUBMIT.
OutputA description of work: log the submission, write the publication, or perform no effect.

A decision is not execution. Evaluating a transition returns its target and output. It does not change your facts, write files, call a model, or store a history. Your caller handles those responsibilities.

03

Define the machine

In your editor, create examples/article-machine.ts. Paste the entire block below and save the file. It contains all types, the word-count guard, and the complete state table.

examples/article-machine.ts
typescript
import { defineMachine } from "../extensions/state-machine.js";

export type ArticleState = "draft" | "review" | "approved" | "published";

export interface ArticleFacts {
  state: ArticleState;
  title: string;
  body: string;
  reviewerAvailable: boolean;
}

export type ArticleChoice = { kind: "approve" } | { kind: "reject" };
export type ArticleEvent = { type: "SUBMIT" };
export type ArticleOutput =
  | { kind: "log-submission"; title: string }
  | { kind: "write-publication"; title: string; body: string }
  | { kind: "none" };

function hasEnoughWords(facts: ArticleFacts): boolean {
  return facts.body.trim().split(/\s+/).length >= 10;
}

export const articleMachine = defineMachine<
  ArticleState,
  ArticleFacts,
  ArticleChoice,
  ArticleEvent,
  ArticleOutput
>({
  stateOf: (facts) => facts.state,
  choiceKey: (choice) => choice.kind,
  eventKey: (event) => event.type,
  states: {
    draft: {
      events: [
        {
          id: "submit-for-review",
          event: { type: "SUBMIT" },
          when: hasEnoughWords,
          target: "review",
          output: (facts) => ({ kind: "log-submission", title: facts.title }),
        },
      ],
    },
    review: {
      choices: [
        {
          id: "approve-article",
          choice: { kind: "approve" },
          when: (facts) => facts.reviewerAvailable,
          target: "approved",
          output: () => ({ kind: "none" }),
        },
        {
          id: "reject-article",
          choice: { kind: "reject" },
          when: () => true,
          target: "draft",
          output: () => ({ kind: "none" }),
        },
      ],
    },
    approved: {
      automatic: [
        {
          id: "publish-approved-article",
          when: () => true,
          target: "published",
          output: (facts) => ({
            kind: "write-publication",
            title: facts.title,
            body: facts.body,
          }),
        },
      ],
    },
    published: { terminal: true },
  },
});

MachineDefinition: the outer object

defineMachine<State, Facts, Choice, Event, Output>(definition) takes one definition object and returns a CompiledMachine. The five type arguments are, in order, your state names, fact snapshot, choice values, event values, and output values. Here they are ArticleState, ArticleFacts, ArticleChoice, ArticleEvent, and ArticleOutput. They are compile-time contracts, not runtime configuration fields.

All four properties of MachineDefinition are required. PropertyKey means string | number | symbol; this recipe uses readable strings.

PropertySignature / typeMeaning and recipe example
stateOf(facts: Facts) => StateReads the current state from each supplied snapshot. (facts) => facts.state is our convention; the SDK does not require a facts property literally named state.
choiceKey(choice: Choice) => PropertyKeyIdentifies an option. (choice) => choice.kind makes approve and reject distinct. choose matches by this key, not object identity or whole-object equality.
eventKey(event: Event) => PropertyKeyIdentifies an incoming signal. (event) => event.type matches a SUBMIT event to the current state’s SUBMIT rules. Other event fields are payload, not additional matching criteria.
statesPartial<Record<State, StateDefinition<State, Facts, Choice, Event, Output>>>A map from state name to its rule object. The key review names the state; the value describes its legal routes. Declaring a name in the state union does not create its table entry. Define every state you will enter, including targets.

There is no initial property. The caller selects the starting state in its first facts snapshot. Calling defineMachine does not enter a state, run a rule, or start a loop. Its returned object exposes advance, choose, and send—not a mutable states or facts property.

StateDefinition: the structure of one state

A state name, a state definition, and the current state are different things. "review" is a name in ArticleState; states.review in the definition is its rules; facts.state === "review" says that this article is currently there. The rule’s id is not the state’s name.

Each state’s value is a StateDefinition<State, Facts, Choice, Event, Output> with these four optional properties. This is a flat state table, not a hierarchy of nested machines.

PropertyType and defaultMeaning and how to define it
terminalboolean; omitted or false means nonterminal.{ terminal: true } marks a finished state. All three operations reject it, even if you also declared outgoing rules. It does not perform a final effect; put that effect on the incoming transition.
automaticreadonly AutomaticRule<State, Facts, Output>[]; omitted means no automatic rules.Routes that need no outside selection. advance returns the enabled automatic transition; it does not execute it or continue to the next state. Our approved state has one publication rule.
choicesreadonly ChoiceRule<State, Facts, Choice, Output>[]; omitted means no choice rules.Options for a person, UI, or model to pick. advance lists enabled options; choose consumes one legal key. Our review state declares approval and rejection.
eventsreadonly EventRule<State, Facts, Event, Output>[]; omitted means no event rules.Routes driven only by send(facts, event). advance does not dispatch these. Our draft state accepts SUBMIT when the article is long enough.

You may omit unused arrays or write []. A state can declare more than one rule collection, but their enabled routes must be unambiguous: automatic and choice routes cannot be enabled together; event routes are checked separately by send. An empty nonterminal state is not an implicit wait or success: advance throws NO_ROUTE.

Define a new state in five moves

  1. Add its name to your State union.
  2. Add a matching key to the definition’s states object. A spelling in the union alone is not a declaration.
  3. Use { terminal: true } if it is finished. Otherwise choose automatic, choices, or events according to what drives its next step.
  4. Give each route an id, when, target, and output; include choice or event for those rule kinds.
  5. Declare each target state, then have the caller supply this new state in its initial facts or reach it through a transition. Exercise both passing and failing guards.

Rule properties: what each route contains

AutomaticRule, ChoiceRule, and EventRule share four required fields. Choice and event rules each require one extra field. There is no implicit guard, output, priority, or destination.

PropertyRequired onMeaning
idEvery rule; string.A diagnostic label such as "approve-article". It helps identify offending rules in failure context. It is not used to select a choice or match an event. Make IDs unique and descriptive; uniqueness is a convention, not an enforced check.
whenEvery rule; a callback returning boolean.The guard: true enables this route for the current facts. Use () => true for an unconditional route. Its arguments depend on the rule kind; see the signatures below.
targetEvery rule; State.The fixed destination, for example "approved". This is a state value, not a callback. The selected target must exist in the table; a self-transition is allowed.
outputEvery rule; a callback returning Output.Builds the transition’s data. It runs only for the selected route, after target validation—not while merely offering choices. () => ({ kind: "none" }) is this recipe’s explicit no-effect output. The SDK does not require a kind or effect field in your own output type.
choiceChoice rules only; Choice.The declared option, such as { kind: "approve" }. Its choiceKey identifies the route. The SDK snapshots object choices; keep them structured-cloneable and free of shared memory.
eventEvent rules only; Event.A declared matching value, such as { type: "SUBMIT" }. The SDK compares its eventKey with the incoming event’s key. Guards and outputs receive the incoming event, including its payload.
Rule kindwhenoutput
Automatic(facts: Facts) => boolean(facts: Facts) => Output
Choice(facts: Facts) => boolean(facts: Facts, choice: Choice) => Output
Event(facts: Facts, event: Event) => boolean(facts: Facts, event: Event) => Output

Choice guards do not receive the picked choice. In a choice output callback, choice is an isolated copy of the declared option, not arbitrary fields supplied by the caller. Matching a legal key does not let a caller replace the declaration’s payload. Event callbacks instead receive the actual event sent in.

All callbacks are synchronous. Keep guards, key functions, and output callbacks deterministic and free of side effects. Facts and arbitrary outputs are not automatically deep-cloned or frozen. Treat the definition as immutable after construction; TypeScript readonly declarations are not runtime freezing.

Construction is not full graph validation. defineMachine snapshots declared choices and can reject an unsupported choice immediately. It does not check every guard combination or target up front: current states are checked when an operation locates them, and targets when a transition is selected. Exercise every route.

Keep the .js import suffixes. The source files are TypeScript, but this repository uses ESM/NodeNext imports. The installed tsx runner resolves these local .js imports to their .ts source files.

04

Write the caller

Create examples/run-article-machine.ts, paste this complete block, and save it. This is the program you will execute. It owns the facts, selects an offered option, and performs the actual file write.

examples/run-article-machine.ts
typescript
import { writeFileSync } from "node:fs";
import type { TransitionDecision } from "../extensions/state-machine.js";
import {
  articleMachine,
  type ArticleFacts,
  type ArticleOutput,
  type ArticleState,
} from "./article-machine.js";

// Run from the repository root; step 1 creates this directory.
const outputPath = "examples/published-article.txt";
let facts: ArticleFacts = {
  state: "draft",
  title: "A small state machine",
  body: "A state machine makes the next legal step explicit. The caller " +
    "supplies current facts, chooses from declared options, and performs " +
    "effects only after the evaluator returns a valid transition.",
  reviewerAvailable: true,
};

function runEffect(output: ArticleOutput): void {
  switch (output.kind) {
    case "log-submission":
      console.log("Submitted for review:", output.title);
      return;
    case "write-publication":
      writeFileSync(outputPath, output.title + "\n\n" + output.body + "\n", "utf8");
      console.log("Wrote:", outputPath);
      return;
    case "none":
      return;
  }
}

function applyTransition(
  decision: TransitionDecision<ArticleState, ArticleOutput>,
): void {
  // If the effect throws, do not claim the transition completed.
  runEffect(decision.output);
  facts = { ...facts, state: decision.to };
  console.log("State:", facts.state);
}

console.log("State:", facts.state);

// draft has event rules only. Start with send(), not advance().
applyTransition(articleMachine.send(facts, { type: "SUBMIT" }));

const offered = articleMachine.advance(facts);
if (offered.kind !== "choices") {
  throw new Error("Expected a choice while the article is in review");
}
console.log("Choices:", offered.choices.map((choice) => choice.kind).join(", "));

// This console recipe deliberately selects approval. In an application,
// collect a human or model pick here, then pass the freshest facts to choose().
const picked = offered.choices.find((choice) => choice.kind === "approve");
if (!picked) {
  throw new Error("Approval is not currently available");
}
applyTransition(articleMachine.choose(facts, picked));

const publication = articleMachine.advance(facts);
if (publication.kind !== "transition") {
  throw new Error("Expected an automatic publication transition");
}
applyTransition(publication);

// published is terminal. Stop here; do not call advance() again.

CompiledMachine: the public evaluator API

The object returned by defineMachine has exactly these three operations. Each call uses your current Facts and returns synchronously or throws. There is no hidden current state, stored offer token, background loop, or automatic effect execution.

Method and return typeWhat it evaluatesWhat the caller does next
advance(facts: Facts): AdvanceDecision<State, Choice, Output>Checks automatic and choice guards in the current state. Returns one automatic transition or the enabled choices. Event rules are not evaluated.Branch on kind. Execute a transition and update state, or present the choices and obtain a pick. A call performs at most one step; it does not chain into the target state.
choose(facts: Facts, choice: Choice): TransitionDecision<State, Output>Rechecks automatic/choice route legality, then matches the supplied choiceKey to one currently enabled option. It does not trust an old offer or caller-supplied payload.Use the freshest facts. Execute the returned output and update state. An option is rejected if its key is no longer legal; the SDK does not track whether you previously called advance.
send(facts: Facts, event: Event): TransitionDecision<State, Output>Matches the incoming eventKey against this state’s event rules, then checks their guards. Exactly one matching rule must be enabled. Automatic/choice guards are not evaluated.Execute the returned output and update state. Our caller uses this to leave the event-only draft state; advance there would throw NO_ROUTE.

How route selection works

  1. Read stateOf(facts), locate its state definition, and reject a terminal state.
  2. For advance or choose, test automatic and choice guards. More than one enabled automatic route, repeated enabled choice keys, or automatic/choice overlap is an error—not a priority rule.
  3. For advance, return the single automatic transition or a nonempty legal-choice list; if neither exists, throw NO_ROUTE. For choose, require a currently legal matching choice key.
  4. For send, inspect event rules separately. An unknown key, no enabled matching rule, or multiple enabled matching rules is an error.
  5. Before returning a transition, check its target exists, then call the selected rule’s output callback. The caller still performs the effect and changes its facts.

Distinct choices may be enabled together; the returned list follows their declaration order for display, not priority. Multiple event rules may share one event key if their guards are mutually exclusive. choose also rejects automatic/choice ambiguity; it is not a way to bypass a conflicting definition.

Returned decisions: every property

AdvanceDecision is a union of ChoiceDecision and TransitionDecision. advance can return either; choose and send always return a transition on success. Check decision.kind before reading shape-specific fields, as the caller above does.

With the recipe’s review facts and an available reviewer, articleMachine.advance(facts) returns this ChoiceDecision:

ChoiceDecision · review
json
{
  "kind": "choices",
  "state": "review",
  "choices": [
    {
      "kind": "approve"
    },
    {
      "kind": "reject"

Choosing approval from those same review facts returns this TransitionDecision:

TransitionDecision · approve
json
{
  "kind": "transition",
  "from": "review",
  "to": "approved",
  "output": {
    "kind": "none"

}
PropertyPresent onMeaning
kindBoth; "choices" | "transition".The discriminant that tells TypeScript and your caller which result shape it has.
stateChoiceDecision; State.The current state in which the options were offered. This result is not a transition and has no from, to, or output.
choicesChoiceDecision; readonly Choice[].The currently enabled, distinct-key options—not rule objects. Object choices are isolated copies. Obtain a pick outside the evaluator and call choose with fresh facts.
fromTransitionDecision; State.The source state read from the supplied facts, not from an internal machine cursor.
toTransitionDecision; State.The validated destination. The SDK does not assign it to facts.state; your caller must do that.
outputTransitionDecision; Output.The selected rule’s returned data. Your domain decides how to interpret it. A returned publication description has not yet written a file.

applyTransition executes decision.output first, then assigns decision.to to our new facts snapshot. If writing fails, this caller throws instead of claiming the article was published. It does not call the rule’s output callback again; that callback already ran inside the evaluator.

The approval selection is deliberately explicit: this recipe finds the offered approve option. A real interface can collect a human pick, or ask a model to select from that same legal list. It must pass the current facts to choose; the evaluator itself never calls the decision-maker.

This is not a durable transaction. The example performs one local write, then updates in-memory facts. An application that needs restart recovery or exactly-once effects must design its own persistence and effect handling. Re-running this example overwrites only examples/published-article.txt.

06

Check the safety rails

A useful machine also rejects illegal operations. Create examples/check-article-machine.ts, paste the complete block below, and save it. These checks use Node’s built-in assertions; there is no extra test framework to install.

examples/check-article-machine.ts
typescript
import assert from "node:assert/strict";
import {
  MachineFailure,
  type MachineFailureCode,
} from "../extensions/state-machine.js";
import { articleMachine, type ArticleFacts } from "./article-machine.js";

function expectFailure(code: MachineFailureCode, operation: () => unknown): void {
  assert.throws(operation, (error: unknown) => {
    assert.ok(error instanceof MachineFailure);
    assert.equal(error.code, code);
    return true;
  });
  console.log("Rejected as expected:", code);
}

const draft: ArticleFacts = {
  state: "draft",
  title: "Safety checks",
  body: "This sample article has enough words to be submitted for review safely.",
  reviewerAvailable: true,
};

// An event exists, but its predicate rejects an article that is too short.
expectFailure("INVALID_EVENT", () =>
  articleMachine.send({ ...draft, body: "Too short" }, { type: "SUBMIT" }),
);

// An event-only state cannot be driven by advance().
expectFailure("NO_ROUTE", () => articleMachine.advance(draft));

const submitted = articleMachine.send(draft, { type: "SUBMIT" });
assert.equal(submitted.to, "review");
assert.equal(draft.state, "draft"); // The evaluator did not update our facts.
const review: ArticleFacts = { ...draft, state: submitted.to };

const offered = articleMachine.advance(review);
assert.equal(offered.kind, "choices");
if (offered.kind !== "choices") throw new Error("Expected review choices");
assert.deepEqual(offered.choices.map((choice) => choice.kind), ["approve", "reject"]);
const approval = offered.choices.find((choice) => choice.kind === "approve");
if (!approval) throw new Error("Expected approval to be offered");

// The reviewer became unavailable after we obtained the options.
// choose() re-evaluates current facts and rejects the now-illegal pick.
expectFailure("ILLEGAL_CHOICE", () =>
  articleMachine.choose({ ...review, reviewerAvailable: false }, approval),
);

const rejected = articleMachine.choose(review, { kind: "reject" });
assert.equal(rejected.to, "draft");
const approved = articleMachine.choose(review, approval);
assert.equal(approved.to, "approved");
const publication = articleMachine.advance({ ...review, state: approved.to });
assert.equal(publication.kind, "transition");
if (publication.kind !== "transition") throw new Error("Expected publication");
assert.equal(publication.to, "published");
assert.deepEqual(publication.output, {
  kind: "write-publication",
  title: draft.title,
  body: draft.body,
});

// Returning an output does not write a file. Only the runner executes effects.
expectFailure("TERMINAL_STATE", () =>
  articleMachine.advance({ ...review, state: "published" }),
);
console.log("All safety checks passed.");

MachineFailure: error API and every failure code

SDK validation failures throw MachineFailure, an Error subclass. Check error instanceof MachineFailure, then handle error.code, whose type is the exported MachineFailureCode union. error.context is a read-only record of structured diagnostics; fields depend on the failure and can include state, operation, ruleId, ruleIds, target, choiceKey, legalChoiceKeys, eventKey, knownEventKeys, or reason. Do not assume every field is present.

error.name is "MachineFailure"; error.message is human-readable, not a stable matching API. Assert on the code, not message wording. The check script above treats expected errors as successful checks; a mismatch exits with a failure.

CodeWhereWhat it means
MISSING_STATEAny operation.stateOf(facts) names a state missing from the table. A state union alone does not create a definition.
TERMINAL_STATEadvance.The current state has terminal: true. Stop driving the machine.
AMBIGUOUS_AUTOMATICadvance, choose.More than one automatic guard passed. Make these routes mutually exclusive.
AMBIGUOUS_ROUTEadvance, choose.An automatic rule and one or more choices are enabled together. Neither has implicit priority.
NO_ROUTEadvance.No automatic route or choice is enabled. This is also expected when you mistakenly advance an event-only state.
AMBIGUOUS_CHOICEadvance, choose.Enabled choice rules have the same choiceKey. Multiple choices with different keys are valid.
ILLEGAL_CHOICEchoose.No enabled choice matches the supplied key, or the state is terminal. The option may have become illegal since it was offered.
UNKNOWN_EVENTsend.This state declares no event rule matching the incoming eventKey. A rule in another state does not count.
INVALID_EVENTsend.The event key is known, but all matching guards returned false.
AMBIGUOUS_EVENTsend.More than one matching event rule is enabled. Declaration order does not break the tie.
INVALID_TERMINAL_EVENTsend.An event was sent to a terminal state. Terminal-event errors differ from advance and choose errors.
INVALID_TARGETAny selected transition.The rule targets an undeclared state. Target validation fails before the output callback runs.
UNSUPPORTED_CHOICEdefineMachine, advance, choose.A choice cannot be isolated, for example because it contains a function or shared memory. Adding a choice rule after construction also violates the captured definition.

Your callback exceptions are not converted into these codes. An exception from stateOf, a key function, a guard, or an output callback propagates as thrown. Distinguish SDK validation failures from bugs in your own callbacks and from effect failures in the caller.

Use the recipe for a different workflow

  1. Replace the five article types with your domain types. Use never for choices or events your workflow does not support; the definition still requires their key callbacks.
  2. Replace the state table and guards. Declare every target state explicitly. Missing or invalid states are rejected at runtime when accessed or selected; defining the machine is not a full graph-validation pass.
  3. Keep automatic routes mutually exclusive, and avoid automatic/choice overlap. Offer multiple choices with distinct keys when a decision is needed.
  4. Change the caller’s effects and input handling. Keep async work, model calls, retries, clocks, and persistence outside the evaluator.
  5. Exercise each new route and the boundary cases. Treat the definition as immutable after construction, keep callbacks pure, and stop driving terminal states.
