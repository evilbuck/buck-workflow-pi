01TL;DR

Six findings that decide everything below.

The workflow spine is already ours

strong overlap

Upstream's main flow — grill → to-spec → to-tickets → implement → code-review — maps almost 1:1 onto b-grill → b-plan/b-nasa-prd → b-phase → b-build → b-review. Ours is deeper at every station (subject folders, cross-references, guardrails ratchet, phased state machine, memory). Do not port the spine.

Part of it is already ported — unattributed

provenance

skills/b-grill-with-docs/CONTEXT-FORMAT.md and ADR-FORMAT.md are near-verbatim copies of upstream engineering/domain-modeling/. Zero attribution anywhere in the repo. Fix before publishing.

Two skills read config nothing writes

dangling dep

b-issue-create and fix-pr both consume docs/agents/issue-tracker.md, docs/agents/triage-labels.md, and the ready-for-agent/needs-triage vocabulary. None of those files exist here, and no skill produces them. Upstream's setup-matt-pocock-skills is the missing producer.

We have no debugging skill at all

P0 gap

The global bootstrap routes "reproducible bug, runtime error" to a systematic-debugger role that does not exist as a skill. Upstream diagnosing-bugs is the single highest-value adoption in the repo.

Review is split across four skills, none two-axis

patch b-review

Upstream runs Standards and Spec as parallel sub-agents so neither masks the other. We have the Spec axis (b-review, single-agent) and the Standards axis (code-review-universal, code-smells) in different skills that never run together.

This repo is a skills factory with no writing standard

P1 gap

writing-for-agents is a reference for authoring skills and AGENTS.md — context pointers, the two loads, progressive disclosure, leading words, no-op hunting. We ship 54 skills and have no such reference. It also directly serves the ongoing bootstrap-consolidation work.

04Overlap deep-dives

The five overlaps where the difference is load-bearing, not cosmetic.

1 · Code review — we have both axes, never in parallel

upstream code-review

Pins a fixed point, resolves the spec from commit-message issue refs, then spawns two sub-agents in parallel: Standards (repo standards + 12 Fowler smells pasted in full) and Spec (missing / scope-creep / wrong-implementation, quoting the spec line). Aggregates without merging or re-ranking — the separation is the point. Both under 400 words.

local

b-review is the Spec axis and the workflow gate: completion matrix with evidence tiers, guardrails contract, in-plan vs out-of-plan routing, iterate-*.md. Single-agent, no fan-out. code-review-universal is the Standards axis with 20+ language guides but no spec contract and no gate. code-smells has 23 smells (superset of the 12) but audits a codebase, not a diff.

Take

Ours is stronger per axis and weaker in composition. Two concrete patches to b-review: (a) run the standards pass as a parallel task sub-agent seeded with code-review-universal's reference guides so it cannot pollute the acceptance-contract context; (b) adopt the no-reranking rule — report per-axis worst finding, never a single winner. A diff-scoped subset of the code-smells catalog is the natural Standards baseline; it already exists.

2 · TDD — we have the loop, they have the seam gate

upstream tdd

Reference, not a procedure. Three rules that bite: test only at pre-agreed seams ("no test is written at an unconfirmed seam"); three named anti-patterns (implementation-coupled, tautological, horizontal slicing); and "refactoring is not part of the loop — it belongs to review".

local b-build

Mandatory red-green-refactor, one test per behaviour, Playwright-first for UI with a verified RED phase, phased-plan state machine, guardrails closeout. Has a TDD Plan step with user approval on behaviours — but confirms behaviours, not seams, and refactor lives inside the loop.

Take

Add skills/b-build/references/seams.md and one line to the TDD Plan step: name the seams under test and confirm them before the first RED. The tautological-test anti-pattern is worth lifting verbatim — the global bootstrap bans padding tests but never names this failure, where the assertion recomputes the expected value the way the code does.

3 · Grilling — one question at a time vs the whole frontier

upstream grilling

Works the design tree in rounds. The frontier is every decision whose prerequisites are settled; ask the whole frontier in one round, numbered, each with a recommended answer. "Finding facts is your job, never the user's" — dispatch a sub-agent for environment facts and only block the questions downstream of it. Done when the frontier is empty.

local b-grill*

One question at a time with a recommended answer. Adds what upstream lacks: question taxonomy, decision-domain tracking, a soft assessment threshold (default 20) that triggers a separation-of-concerns evaluation feeding b-phase, durable grill-session-*.md, an auto-mode that answers via a different model over Pi RPC and records divergence.

Take

Ours is the richer skill; upstream has the better pacing primitive. Round batching cuts a 20-question grill from 20 turns to ~5 without losing dependency ordering, and the "facts are the agent's job, dispatch a sub-agent, don't block the rest of the frontier" rule is a straight improvement. Offer it as a mode, not a replacement — one-at-a-time is better for dictation-style sessions.

4 · Tickets — dependency typing vs a grabbable frontier

upstream to-tickets + implement-spec

Vertical tracer-bullet slices, each sized to one fresh context window, each declaring blocking edges as native tracker links so the frontier renders in the tracker UI. implement-spec then runs implementer sub-agents across the ready frontier in parallel worktrees, merges each into one PR branch, recomputes the frontier, and runs /code-review at the end. Wide refactors get an explicit expand–contract sequence.

local b-phase + b-auto-fix

b-phase is the only local skill that types dependencies (HARD / SOFT / NONE), writes a dependency matrix, sets depends_on, and notes parallel opportunities — but execution is still "phase N, then N+1". b-auto-fix runs one issue per worktree, sequentially through research→plan→build→review.

Take

We already compute the graph and then throw the parallelism away. Two cheap wins: (a) b-phase emits an explicit ready frontier (phases with all HARD deps satisfied) instead of only a linear order; (b) b-auto-fix gains a frontier mode that runs the NONE-dependency set concurrently and merges per completion. The expand–contract recipe for wide refactors has no local equivalent and is worth a section in b-phase.

5 · Research — the skill contradicts the bootstrap

Live drift

The global bootstrap says: "b-research — Always delegate to a subagent. Never bundle external research into the main agent's context. Run asynchronously when helpful." skills/b-research/SKILL.md describes no background or sub-agent dispatch at all — it reads as a foreground procedure. Upstream research is three sentences and its first word is "Spin up a background agent".

Ours is otherwise far deeper (incremental write-gate, source dictionary, sources-*.md with access dates and quotes, canonical consolidation every 3–5 sources, informs: cross-refs). Only the dispatch mode is missing. Nothing to port — a drift to close.

05Genuine gaps

Nine capabilities upstream has that this repo has no counterpart for.

diagnosing-bugs

P0

Why it matters here: the global bootstrap's task-routing table sends "reproducible bug, runtime error" to systematic debugging — a role with no skill behind it. b-build assumes you know what to build; b-iterate assumes the defect is already written down in iterate-*.md. Nothing owns "it's broken and we don't know why".

the load-bearing idea

Phase 1 is the whole skill: refuse to hypothesise until one named command already went red on this bug — tight, deterministic, fast, agent-runnable. Ten ranked ways to construct one, from failing test down to a human-in-the-loop bash driver.

integration

buck loop New on-ramp /b-diagnose. Feeds b-iterate (fix in place) or b-plan (architectural). Its Phase 5 "no correct seam exists — that itself is the finding" hands off to code-smells, exactly like upstream hands off to improve-codebase-architecture.

triage

P1

Why it matters here: every issue-facing skill we own points outward — b-issue-create publishes, fix-pr and b-pr-review-2-issues consume our own PR feedback, b-auto-fix executes already-ready issues. Nothing turns a raw inbound report into a ready-for-agent issue, which is precisely the state b-auto-fix requires as input.

the load-bearing idea

Redundancy + prior-rejection checks before anything else; verify the claim (reproduce the bug, check out the PR) before grilling; durable agent briefs written behaviourally with no file paths or line numbers because the issue may sit for weeks; a .out-of-scope/ knowledge base so the same rejected request is not re-litigated.

integration

buck loop Inbound on-ramp: /b-triage → b-issue-create (or direct label) → b-auto-fix. Closes the loop we currently only half-own. Depends on the tracker config below.

writing-for-agents

P1

Why it matters here: this repo's entire product is documents agents consume. It also directly serves the open bootstrap-consolidation work (GLOBAL_OR_PROJECT-AGENTS.md duplicate-policy audits).

the load-bearing idea

Context load (tokens every turn) vs cognitive load (the human as index); the information hierarchy (in-file step → in-file reference → disclosed reference); completion criteria graded on clarity and demand; leading words that recruit pretrained priors; and the no-op test — does this sentence change behaviour versus the default? Plus: negation makes the forbidden behaviour more available, so prompt the positive.

integration

standalone Model-invoked reference. Pull it in from b-init-factory and from any session editing AGENTS.md/SKILL.md. No loop position.

codebase-design

P1

Why it matters here: b-plan, b-build, code-smells and b-arch-qa all discuss module shape with no shared vocabulary, so each session re-invents "service" / "component" / "boundary".

the load-bearing idea

Seven terms used exactly (module, interface, implementation, depth, seam, adapter, leverage, locality); depth defined as leverage at the interface, explicitly rejecting Ousterhout's line-ratio; the deletion test; "the interface is the test surface"; "one adapter is a hypothetical seam, two is a real one". DESIGN-IT-TWICE.md adds a 3–4 way parallel sub-agent interface bake-off.

integration

standalone Vocabulary reference underneath b-plan, b-build (seams), code-smells, and any adopted b-diagnose. Pairs with the seams gate above.

wizard

P1

Why it matters here: zero local skills generate a runnable script for a human. Every credential setup, dashboard walk, and one-off cutover is currently re-explained to an agent from scratch.

the load-bearing idea

The UX is pre-solved in template.sh (8.5 KB: staged progress, confirmation gates, cross-platform URL open including WSL, hidden secret entry, idempotent .env upserts, gh secret writes). The skill only scopes stages and authors them. Verified statically — never run end-to-end, since it blocks on human input.

integration

standalone Model-invoked; fires when an agent hits a wall only a human can pass. Optional tie-in: b-init-guardrails could emit a wizard when tooling needs credentials.

setup-matt-pocock-skills → b-init-tracker

P0

Why it matters here: it is the missing producer for config b-issue-create and fix-pr already read. Adopting a trimmed version costs an hour and removes a live inconsistency.

trim to

Section A (issue tracker: GitHub / GitLab / local markdown / other) and Section B (triage labels) only. Section C (domain-doc layout) is already covered by b-docs + CONTEXT.md. Its ## Agent skills managed block is the same idempotent-marker pattern b-init-guardrails uses.

integration

buck loop One-shot repo init beside b-init-guardrails. Hard prerequisite for an adopted b-triage.

handoff

P1

Why it matters here: b-recap is chat-only orientation and explicitly not a checkpoint; b-save is a durable historical record, not a bootstrap prompt. Neither produces a portable document that seeds a fresh agent — cross-harness (OMP → Claude Code), cross-directory, or cross-machine.

the load-bearing idea

Write to the OS temp dir, not the workspace. Include a "suggested skills" section naming what the next agent should load. Reference specs/plans/ADRs/commits by path or URL rather than duplicating them. Redact secrets.

integration

buck loop Sits at the session boundary next to b-recap and b-save. Cheap: ~40 lines. Also unlocks the prototype detour (out-and-back handoff).

prototype

P2

Why it matters here: b-brainstorm, b-grill, and b-arch-qa all try to settle design questions in prose. Some questions ("does this state machine feel right?", "what should this look like?") are not settleable in prose, and we have no cheap escape hatch — design-brief and b-create-ux-guide document intent, they do not produce something to react to.

the load-bearing idea

Branch on the question: state/logic → one shareable HTML file with free-play buttons and guided walkthroughs a non-developer can drive; UI → several radically different variants on one route, switched by a URL param. Throwaway is a constraint on how it's written, not a promise to destroy it — the artifact is kept as a primary source on a prototype/<name> branch.

integration

buck loop Detour from b-brainstorm/b-grill, returning via b-handoff. Its output is a decision that feeds b-plan.

wayfinder

P2 — evaluate

Why it matters here: b-phase decomposes execution once the shape is known. Nothing decomposes uncertainty when it isn't. The gap shows up as sprawling b-brainstorm sessions on greenfield work.

the load-bearing idea

Name the destination first (it fixes scope). Tickets are decisions, not slices. Four ticket types (research AFK, prototype HITL, grilling HITL, task). Fog of war: don't chart what you can't phrase sharply yet — ticket when the question is sharp even if blocked, fog when it isn't. Never resolve more than one ticket per session. When the map clears, hand off to to-spec; do not loop straight into implementation.

integration

buck loop if adopted: pre-b-plan on-ramp for multi-session efforts, terminating in b-plan. Caveat: heaviest skill in the library, tracker-dependent, and overlaps b-brainstorm + b-grill + b-phase. Adopt only after b-triage proves the tracker integration works.
