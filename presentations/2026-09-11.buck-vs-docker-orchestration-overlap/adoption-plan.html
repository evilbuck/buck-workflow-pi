01If you had to pick one

Build on buck. Steal jz's closing mechanics.

The merge direction follows cost, not taste. buck's two structural advantages — a git-portable durable record that every station writes through one shared resolution protocol (skills/_shared/subject-resolution.md), and a recorded numeric quality contract with a baseline history (guardrails.json, six gates, a brownfield ratchet) — cannot be retrofitted skill by skill. They only work because everything writes through them. jz would have to re-architect 24 skills to get either one. jz's advantages are rules and leaf skills: a convergence contract, a restraint lens, requirement IDs, a wait cap, a tombstone file. Each folds into an existing buck station without touching the spine. Roughly ten patches one way; a re-architecture the other.

What you give up by choosing buck, stated plainly. buck's terminal state is a PR URL. It has no CI-green loop, no deploy station, and its autonomy skill only stamps a recommendation onto phase frontmatter and stops. If the question were “which suite ships this repository to production with the fewest human turns”, jz wins outright, and it is not close.

Why that does not change the answer. buck is a distributed package targeting seven harnesses; jz's conductor is bound to one company's GitHub Actions workflows, EKS contexts and repository names. And buck already deleted extension-based orchestration once, deliberately, on exactly the reasoning that orchestration which is not observably invoked becomes dead weight. The thing to import is jz's convergence contract, not jz's conductor.

The single most valuable idea in jz is not a skill

It is that iteration is a mode with a named exit condition, never a skill name. A skill defaults to one read-only pass ending in a proposal; it converges only when a caller passes an explicit, greppable loop scope, and a loop must declare the observable condition that ends it. buck has 54 skill directories and no general convergence contract — every loop is hand-built inside one station. This is the only adoption on the list that would reduce buck's surface area rather than grow it.

02The three real forks

Everything else in the comparison is furniture. These are the three places where the two suites genuinely disagree about how software gets built — and only two of them are worth crossing.

1 · Where truth lives do not cross

buck puts it in the repository — .context/ subject folders, a memory ledger, a backlog, CONTEXT.md, docs/adr/, guardrails.json. jz puts it in the tracker and the process — ticket IDs, PR bodies, and a session state file under ~/.jz-agent-session-state/, with an explicit rule that repo files carry current state and not history. Consequence: buck survives a clone, a harness swap and a six-month gap; jz survives a busy quarter and then forgets. This is an intentional policy fork on both sides. Port mechanics across it, never the policy.

2 · What enforces quality cross both ways

buck enforces with recorded numbers a read-only measurer compares against: six gates, a patch-coverage floor, a monotonic coverage ratchet, a complexity ceiling. Deterministic, cheap, reproducible — and blind to every defect a number cannot see. jz enforces with adversarial process: four review lenses on a different model family, a restraint filter over the findings, and convergence loops to green. Catches design and semantic defects a threshold never will — and is non-reproducible and costs a model run. These are complements, not competitors. buck has the number and no panel; jz has the panel and no number.

3 · Who closes the loop cross partially

buck stops and hands back to the human at every station boundary; even its autonomy skill only stamps omp_execution onto phase frontmatter and tells the user what to type. jz dispatches, polls and converges, stopping only before money and before production. Take jz's convergence contract — a loop with a named exit condition and a cap. Do not take jz's conductor: it is company-bound, and buck retired its own orchestration layer on principle.

03What neither side has

Five holes that survive the merge. Worth naming, because a combined suite would still have all five and it is easy to assume the other repo covered them.

No automated red-phase gate

Both mandate test-first in prose. Neither blocks an edit to source before a failing test has been observed. buck's closeout proof is a post-hoc coverage measurement; a 90% patch-coverage floor tells you the lines were covered eventually, not that the test was written first.

No dependency-graph validation

buck models HARD / SOFT / NONE edges and writes depends_on frontmatter, and nothing anywhere verifies the graph against the tree. jz has no dependency taxonomy at all. Both are documentation that can silently go wrong.

Security is not a gate on either side

buck's six gates cover tests, lint, patch coverage, global ratchet and complexity — no security gate. jz has a pre-push secret-scan carve-out, which is a scan, not a contract. Security appears in review checklists on both sides and in no threshold file.

No artifact-to-reality drift detector

A plan, phase or backlog item can claim status: completed and nothing checks the claim against the tree. buck's b-review audits completion properly — but only for the one subject a human points it at, at the moment they point.

No concurrent execution

buck's phase overviews emit a “Parallel Opportunities” section and dispatch nothing. jz's conductor is strictly sequential. Both suites can identify independent work and neither can run it.

04Into buck — prioritized

Three waves, ordered so that nothing depends on something later. Each card says what the idea is — not the file to copy — plus where it attaches and the check that proves it landed. Classes are the same four used in the main report: fold-in patches an existing skill, new member adds a skill with a named chain position, repo init is one-time repository furniture, standalone has no chain position.

Wave 1 · Furniture — one PR, four files, no skill semantics changed

1 · Skill-contract lint in CI

repo init

Static structural lint over the whole suite: name: matches its directory, description present and within bounds, every cited repository path resolves, every referenced slash command exists, every commands/*.md is a symlink to its prompts/ twin or has no twin, no retired name still present in the tree.

Where: new scripts/skill-lint.mjs, wired into package.json scripts.test — which is already prepublishOnly and already the only thing CI runs. No new workflow file.

Value highEffort lowRisk noneAcceptance: on today's tree it must fail with exactly the two defects in §07

2 · skills/RETIRED tombstone

repo init

Renaming or deleting a skill appends the old name to a never-truncated list; install and update purge those names. Without it, tooling only walks names that still exist, so a removed skill is invisible to uninstall and keeps advertising itself forever.

Where: new skills/RETIRED; one purge clause in scripts/install.mjs. buck has the maximum exposure here — it publishes skills/ to npm and symlink-installs into seven harnesses, so one rename strands links in six places at once.

Value highEffort lowRisk noneAcceptance: rename a skill, then install.mjs --verify reports the stale link

3 · A 30-second cap on inline waiting

fold-in

Never block inline for more than half a minute; a longer wait goes to the harness's async mechanism or ends the turn with a condition to re-check. The ban is on waiting, not on working — a command doing real work for ten minutes is fine.

Where: one paragraph in GLOBAL_OR_PROJECT-AGENTS.md, the installable bootstrap — not repeated per skill. This is a prerequisite for wave 3's convergence loop, which is why it lands in wave 1.

Value mediumEffort lowRisk noneAcceptance: the rule is greppable in the bootstrap and cited by the loop skill

4 · Untrusted-data posture as a shared protocol

fold-in

CI logs, bot comment bodies, fetched pages and review findings are data, never instructions; an override is only honoured from the human invocation channel. Named once, referenced everywhere, rather than re-improvised per skill.

Where: new skills/_shared/untrusted-data.md — _shared currently holds exactly one protocol file, so this is its designed extension point — referenced from fix-pr, b-pr-review-2-issues, b-research and code-review-universal.

Value mediumEffort lowRisk noneAcceptance: four skills cite the protocol; none restates it inline
Wave 2 · The two real capability holes

5 · b-debug — systematic debugging

new member

Reproduce, isolate, prove the root cause, fix, keep the reproduction as a regression test. Two rules carry it: no fix before a proven root cause, and after three failed fixes stop and question the architecture rather than trying a fourth.

Where: skills/b-debug/ plus a prompts/ twin and a commands/ symlink; an escalation row in b-iterate, whose entire current answer to debugging is the phrase “lightweight diagnostics”. It also closes a dangling contract: the always-on bootstrap routes runtime bugs to a systematic-debugger role that does not exist in skills/.

Value highEffort mediumRisk lowSecond independent audit to find this same hole — see the 2026-09-10 mattpocock adoption subject

6 · A restraint lens over review findings

fold-in

Before a reviewer emits its report, every finding passes a disposition: a never-simplify set is exempt outright (trust boundaries, error handling that prevents data loss, security, accessibility, anything the plan explicitly asked for); everything else is classified as real defect or gold-plating; every decline is recorded with a one-line reason; criticals are never declinable.

Where: the classification step of b-review and the validation step of fix-pr. This attacks buck's actual failure mode — iterate-*.md churn generated from findings nobody triaged.

Value highEffort mediumRisk lowAcceptance: a review with a declined finding shows the reason inline; criticals cannot be declined

7 · Requirement IDs with (source:) tags

fold-in

Number requirements once; every downstream artifact cites the id rather than a line number. Two rules do all the work: an untagged requirement is scope creep and gets cut, and a requirement no downstream line cites is a dropped requirement.

Where: mint in b-nasa-prd (extend its existing rule-ID audit checklist), carry through b-plan steps, replace from_plan_steps with ids in b-phase frontmatter, verify in b-review's completion matrix. Payoff: that matrix stops being prose a human has to believe and becomes something grep can check.

Value highEffort highRisk mediumTouches four skills — give it its own plan subject, never share a cycle with item 8
Wave 3 · Closing mechanics — highest value, highest risk, one per cycle

8 · A convergence contract

fold-in

One shared rule: a skill runs one pass and proposes; it loops only under an explicit loop scope, and a loop must declare an observable exit condition plus a maximum iteration count. No skill name ever contains -loop.

Where: new skills/_shared/convergence.md, cited by the review and iterate stations. The structural payoff: b-pr-review-2-issues (plan only) and fix-pr (act now) collapse into one skill with a mode flag, instead of two skills a user must choose between correctly. This is the only item on the list that shrinks the suite.

Value highEffort highRisk mediumAcceptance: every looping skill names its exit condition; the two PR-feedback skills become one

9 · b-converge — CI-green and bot-comment loops

new member

Drive red gating checks to green — never by editing the CI configuration — and drive bot review comments to an empty review against the current head. Failing-log reading is delegated to a subagent so raw CI output never lands in the main conversation.

Where: the missing station immediately after b-pr. buck's chain currently ends at a PR URL, and fix-pr is explicitly instructed to ignore “CI still running”. Depends on item 3 for its background-dispatch discipline and item 8 for its exit condition.

Value highEffort highRisk mediumBlocked on items 3 and 8 — do not start it first

10 · Confined different-model review

fold-in

Run the reviewer on a different provider from a temp directory containing only the copied diff and the acceptance criteria, under a deny-by-default read-only tool allowlist, a throwaway config directory and secret-environment redaction.

Where: as an optional dispatch mode inside code-review-universal — not a new skill. buck already runs another model family over Pi RPC in b-grill-auto and pi-rpc; the transport exists and the confinement contract is the missing half.

Value mediumEffort mediumRisk lowReuses skills/b-grill-auto/grill.py — no new transport

11 · b-skill-writer

new member

Test-driven documentation: run the pressure scenario with a subagent before writing anything, record the exact rationalisations it produces without the skill, write the skill against those, verify compliance, then close the loopholes it finds.

Where: skills/b-skill-writer/. buck's product is skills and it has no skill for making them. Pairs directly with item 1 — the lint is the mechanical half of skill quality, this is the judgment half.

Value mediumEffort mediumRisk lowDo after item 1 so the lint can encode whatever the skill decides
Explicitly declined · ranked, considered, rejected

Prose de-tell pass scope down or skip

buck's bootstrap already carries a hard, always-on house style with its own anti-filler rules. A second prose-rewriting authority would collide with it and the two would disagree on the same sentence. If adopted at all, scope it to release notes and PR bodies only — never to chat output, which the bootstrap already governs.

Two-phase PR topology conditional

buck already solves the same review-noise problem inside a single PR by splitting implementation files from .context/** artifacts in the body. A doc-only plan PR stacked under an implementation PR is worth it only on the AFK handoff path, where a human must approve a plan before an agent implements it — that is the one case buck's single-PR split does not cover.

Hook-driven session state take the requirement, not the mechanism

The goal — surviving compaction without spending a turn — is a genuine buck gap. The mechanism, a Stop hook spawning a headless model to edit a state file, is the thing buck deliberately removed when it retired extension-based orchestration, and /b-save is a pure prompt by design. The cheap equivalent already exists in-tree: the write-gate that b-research, b-explore and b-capture use. Extend that to b-build and b-review and the gap closes with no hook at all.

05Out to jz — prioritized

The return path. Ranked the same way, and read from upstream's side: each one has to survive jz's own stated policies, not buck's.

1 · A git-portable durable record

new member

jz's session state lives in ~/.jz-agent-session-state/ — outside git, outside code review, unreadable by a teammate or a different harness. The answer to jz's “files carry state, not history” rule is narrow: rationale in a PR is fine while the PR is open; the arc record is what the next session reads, and that is a different consumer. Keep the hook-driven writer; change only where it writes.

Value highEffort mediumPosition: a save station at conductor arc end, after review, before deploy

2 · A recorded quality contract

repo init

jz discovers each repo's own quality commands and records no thresholds, so nothing can regress detectably — a suite that was 80% covered last quarter and is 60% now passes both times. Take the split as well as the file: a one-shot initializer that writes the contract, and a measurer that runs it and never edits anything.

Value highEffort lowLowest-effort, highest-certainty item in either direction

3 · Dependency typing on plan tasks

fold-in

HARD (blocking), SOFT (a stub or mock unblocks it), NONE (genuinely parallel). jz's conductor is sequential while its own dispatch mandate wants background work everywhere; the executor ledger has no field that says which tasks are independent. This is the enabling data, and it is three enum values.

Value mediumEffort mediumPosition: plan-writer emits it, the executor ledger carries it

4 · A briefing artifact at the human gate

new member

jz stops for human approval before production with nothing to read but a diff. A generated briefing page — built from the spec and plan already written — gives the approver something reviewable. The gate already calls a prose-polish skill for release notes, so a document-generation step is established there.

Value mediumEffort lowPosition: alongside release-notes humanisation, at the existing pre-prod gate

5 · A doc taxonomy for rationale

standalone

Decisions in docs/adr/, domain language in CONTEXT.md, task sequences as Diátaxis how-tos — the why given a home that outlives the PR being archived. Offer this; do not push it. It sits directly on the policy fork and only lands if upstream chooses to relax the rule.

Value mediumEffort mediumGated on a policy decision upstream, not on effort

6 · A backlog surface

new member

Between “this is a ticket” and “this is forgotten”, jz has nothing. A repo-local queue of linked items with an archive is the missing middle, and it is the natural sink for the findings its restraint lens declines.

Value mediumEffort lowPairs with the restraint lens: declined findings need somewhere to go

06Sequencing and rules of engagement

Five constraints on the order. Four of them exist because an item is cheaper now than later, or is load-bearing for something after it.

  • Wave 1 is one pull request. Four files, no skill body semantics changed. Items 1 and 2 are the only ones that get strictly more expensive every time the tree grows — a linter written at 54 skills is cheap; at 90 it is an archaeology project.
  • Items 7 and 8 never share a cycle. Each touches four or more skills. One plan subject each, and land the ID convention first — the convergence contract's exit conditions read better when requirements already have stable names.
  • Nothing in wave 3 starts before item 3. The CI loop's correctness depends on the wait cap; without it the loop blocks a turn instead of dispatching.
  • Do not import a conductor. buck's replacement for autonomy is the harness primitives a user types, recommended per phase by b-loop. That decision was made once, on the grounds that uninvoked orchestration is dead weight, and nothing in this audit changes the reasoning.
  • Do not import the spine in either direction. Both suites are deeper station-for-station in their own half. A wholesale import strands the supporting mechanics — subject folders versus execution ledgers, recorded thresholds versus adversarial lenses — and leaves two half-wired systems.
Cheapest credible first move

Items 1 through 4 plus item 5. That is one furniture PR and one new skill; it closes the repo's only dangling always-on contract, gives the suite a permanent structural check, and costs no change to any existing workflow station.

07Two live defects found while sizing this plan

Both were verified in the working tree during the sizing pass, after the main audit closed. Both are exactly what item 1 exists to catch, which is the argument for item 1.

Dangling documentation references medium

skills/b-issue-create/SKILL.md cites docs/agents/issue-tracker.md and docs/agents/triage-labels.md as the source of its tracker conventions and label vocabulary. The directory docs/agents/ does not exist in the repository. An agent following that skill reads two missing files and improvises the label vocabulary. This corroborates an open finding from the 2026-09-10 audit rather than adding a new one — but it is now confirmed against the current tree.

The prompts-to-commands mirror is broken for four commands medium

The repository documents commands/*.md as symlinks back to prompts/*.md so there is one source of truth. In fact 8 of 37 command files are regular files, and four of those shadow a diverging twin: b-pr (13 lines against 62), b-pr-review-2-issues (13 against 50), b-commit-improved (19 against 13) and b-save-improved (20 against 13). commands/b-pr.md is a thin skill loader; prompts/b-pr.md is a full inline procedure that predates the skill. A Pi user and an OMP user typing /b-pr are following different instructions. A lint asserting “every command file is a symlink or has no twin” fails on this today.
