Two agent workflows, compared

Both repositories teach an AI coding agent how to do software work. They were built independently, they share an ancestor, and they solve opposite halves of the same lifecycle. This report catalogues every skill on both sides, organises them by the question they answer, and says exactly where the two overlap.

01Bottom line

They are the same kind of thing, aimed at different halves of the job.

buck-workflow-pi is broad and artifact-centric. Its 53 skills cover the widest possible arc — from a dictated idea, through research, requirements, plans, phases, UX guides and briefing decks, all the way to a committed session record and a documentation taxonomy. Almost everything it does leaves a durable file in git.

docker-orchestration's .claude is narrow and gate-centric. Its 24 skills cover a shorter arc — ticket, spec, plan, execute, review, PR, green CI, merge — but each station has more machinery: a multi-model review panel, an execution controller with a resumable ledger, two convergence loops, and one conductor that drives the whole thing with exactly three points where a human must say yes.

Neither is a subset of the other, and neither should absorb the other's spine. The value in each direction is single rules, gates and vocabulary.

  • The overlap is real but shallow. Of the eight lifecycle stages, none is a straight duplicate; three are strong overlap with one side materially deeper, three are partial, two are adjacent.
  • The biggest single gap in buck is the build station. jz has a task-by-task execution controller, an enforced TDD law, a root-cause debugging skill and a persistent restraint lens. buck has one builder skill and no debugging skill at all.
  • The biggest single gap in jz is durable memory and meaning. Its session record lives outside git and its rules ban rationale from repo files. buck has a committed session ledger, a backlog, ADRs, how-tos and domain-language docs.
  • Both are honest about being derivative. Seven jz skills are declared MIT ports of the same open-source library whose lineage also reaches buck — and one of the two repos already ships the attribution file the other one needs.
  • Three upstream housekeeping conventions are worth copying on their own merits, independent of any skill: a skill linter in CI, a tombstone file for retired skills, and a rule that a skill runs one pass unless a caller explicitly asks it to loop.

02How to read this

Six terms carry most of the weight. If you know these, everything below reads straight through.

SkillA Markdown file (SKILL.md) that teaches an AI coding agent how to do one job well. The agent loads it on demand when the job comes up. Think “runbook the agent actually follows”, not documentation a human reads.
Slash commandA short alias a person types — /b-plan, /pr — that loads a skill. Thin by design: the command routes, the skill contains the thinking.
HarnessThe program the agent runs inside: Claude Code, Pi, OMP, OpenCode, Codex. Skills are portable between harnesses; hooks and extensions usually are not.
SubagentA second agent spawned with a narrow brief and a clean context window. Used to review work, run a task in isolation, or read something bulky without polluting the main conversation.
GateA point where the workflow refuses to continue — a failing test, a missing requirement, a human who has not said yes yet. Gates are the load-bearing part of both suites.
Loop modeRunning a review-and-fix cycle until it comes out clean, rather than reporting once and stopping. Who is allowed to start a loop turns out to be a real design decision.
DuplicateSame job, same mechanics
Strong overlapSame job, one side materially deeper
Partial overlapThe job is split differently across skills
AdjacentNeighbouring job, different output
No overlapOne side has it, the other does not

03The two projects

Same genre, very different centre of gravity. One is a product whose whole purpose is the workflow; the other is a workflow that grew inside a working infrastructure repo.

buck-workflow-pi

A standalone, published toolkit
What it is
A distributable collection of agent skills, slash commands and one runtime extension. The workflow is the product.
Shape
Three layers: portable skills are the source of truth, thin prompt/command wrappers are the invocation surface, a small TypeScript extension handles runtime hooks.
Reaches
Pi, OMP, Claude Code, OpenCode, Codex, Grok and Goose — via package install, a symlink installer, or a marketplace plugin.
Signature move
Everything meaningful lands in a dated subject folder under .context/, and the session ends with a committed memory record.
Audience
Any repository, any stack. Nothing is company-specific.

docker-orchestration · .claude/

A team's toolkit, living inside their dev-environment repo
What it is
The agent tooling one engineering team maintains for itself, kept in the repo that already holds their local Docker harness.
Shape
Six surfaces: skills, four slash commands, a global rules file, session hooks, a terminal status line, and an output style — each with its own install model.
Reaches
Claude Code and OpenCode via one installer command; Pi comes along free because the installer writes to a shared skills directory.
Signature move
Reviews run on a different AI provider than the one doing the work, in a locked-down sandbox, and return a verdict.
Audience
Mostly portable, but six skills are welded to the team's own infrastructure by design.

Why this matters for buck-workflow-pi

An audit on 10 September found that two reference files under skills/b-grill-with-docs/ are near-verbatim copies of a different MIT-licensed skill library, with no notice — and that package.json publishes skills/ to npm, which makes it a licence condition rather than a courtesy. That remediation is already planned. What this audit adds is a working template: a peer repository facing the same obligation ships a single root file with source, author, pinned version, licence text and a per-skill port table, and treats it as routine.

Iteration is a mode, never a name

fold-in

A skill defaults to one read-only pass ending in a proposal. It converges only when the caller passes an explicit, greppable loop scope — because a prose cue can be edited away and silently leave a call site one-shot. Never put -loop in a skill name.

Skill lint in CI

repo init

Static structural lint over every skill: name: matches the directory, description present and within spec, every cited file path resolves, every named sub-skill and slash-command target exists, hook scripts executable. buck already has a known dangling-reference defect of exactly this class; a lint catches the whole family, permanently.

A RETIRED tombstone file

repo init

Renaming or deleting a skill appends the old name to skills/RETIRED; install/update purge those names, status reports leftovers. Without it, tooling only walks names that still exist, so a deleted skill is invisible to uninstall and keeps advertising itself forever. buck publishes to npm and symlink-installs into seven harnesses — it has the exact exposure.

10What not to port

A list of non-goals is as useful as the adoption list. These are the things that look transferable and are not.

Never port the spine

Each suite is deeper station-for-station in its own half. Importing jz-spec-writer or jz-plan-writer wholesale would replace mature buck skills with ones tuned for a different repo's conventions. Take single rules, gates and vocabulary — not workflows.

The six company-bound ops skills

jz-cert, jz-kibana-search, jz-kafka-connect-api, jz-zuora-invoice-writeoff, jz-dev-commands and jz-deploy hard-code internal hostnames, repo names, AWS profiles and GitHub Environments. They are correct there and meaningless anywhere else.

Anything requiring the jz shell dispatcher

A large part of the suite assumes bin/jz, ~/.jz.sh and a container toolchain. Porting the instruction without the dispatcher gives an agent commands that do not exist.

jz-cycle-doc

It reproduces an external template pinned to a specific upstream revision. Without that upstream the artifact has no contract to satisfy.

The Claude hook contract itself

The session-state hooks are Claude Code-specific. Copy the design — out-of-band writer, injected at session start, precedence over the compaction summary — not the shell scripts. buck's own history already argues against new extension-based orchestration.

Attribution, already open medium

Dangling references have no detector medium

buck's skills cite docs/agents/issue-tracker.md and docs/agents/triage-labels.md, which no skill produces and which do not exist. That is precisely what jz skill-lint check exists to catch, and it runs in CI upstream. The defect is known; the missing piece is the detector.

No tombstones while publishing and symlinking low

buck installs into seven harnesses by symlink and publishes to npm. A renamed or deleted skill stays on every machine that installed the old revision, invisible to any uninstall path that walks only current names.

A routed role with no skill behind it low

The global bootstrap's task-routing table sends “reproducible bug, runtime error” to a systematic-debugger role. No such skill exists in the 53. Two independent audits have now found it.

Nothing to action on the upstream side info

The upstream repo's own housekeeping is in order: attribution is present and complete, the skill lint runs in CI, the destructive-script marker convention is documented, and the one financially dangerous skill enforces its guardrails in Python rather than in prose.

12Method & evidence

How this was produced, and where the working notes live.

Read-only throughout

Neither repository was modified. The upstream repository was cloned to a temporary directory at commit 1fea15e and read; the local repository was read at commit f797174. No skill, prompt, extension or configuration file in either tree was written to.

Split reading

Seven read-only research agents catalogued the local suite in six disjoint clusters plus the upstream company-specific tail, each returning the same contract — invocation, input, exact output paths, workflow position, distinctive mechanic, stated non-goals. The upstream workflow spine was read directly rather than delegated, because the value in a peer library is usually a single rule inside an otherwise-familiar skill, and that does not survive summarisation.

Working notes

Raw per-cluster reports and the durable findings artifact are under .context/2026-09-11.resumator-docker-orchestration-overlap/ — seven cluster reports in research/, the first-pass upstream notes in research-overlap-notes.md, and the full synthesis in research-overlap-findings.md, including the open-questions list this report omits.

Counting convention

buck-workflow-pi has 54 directories under skills/; _shared is a protocol registry rather than a skill, so the headline count is 53. Two buck skills (b-loop, b-auto-fix) and two jz skills (jz-adversarial-review, jz-senior-engineer) are listed in two stages because they genuinely operate in both.
