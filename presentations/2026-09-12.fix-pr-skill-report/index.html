fix-pr — from review comments to a settled PR

A step-by-step walkthrough of the fix-pr skill: work in a git worktree on the PR's real head branch, validate every comment against current code with parallel subagents, fix every valid finding by default, push, then poll for an independent re-review and repeat until the PR is settled. Each step is tagged so you can see what the machine does, what the model judges, and what gets delegated.

📄 skills/fix-pr/SKILL.md 🔧 scripts/fetch-feedback.sh 🌳 worktree pinned to headRefName 🔁 poll-until-settled (default 10 loops)
Skill-only — no prompts/fix-pr.md wrapper Agent-agnostic: needs only git + gh + a test runner
Deterministic
Fixed commands and scripts. Same input → same output. No judgment required.
LLM judgment
The mainline model reads, reasons, and decides. Quality depends on the model following the skill.
Subagent
Dispatched as a parallel, read-only task to keep raw PR payloads out of mainline context. Never mutates.
Decision gate
A branch point with hard rules — mode flags, settlement, or the loop cap — not a judgment call.

The whole flow at a glance

1 · Identify PR + worktree→ 2 · Inventory feedback→ 3 · Validate vs code→ 4 · Choose disposition→ 5a · Fixor 5b · File issues→ 5c · Poll & repeat→ 6 · Record & close

Steps 1 and 3 fan work out to read-only subagents to keep raw payloads out of the mainline's context; the mainline still owns every verdict, edit, commit, push, and the settlement call. Step 0 (below) is where you choose how far a run is allowed to go.

0

Pick your mode — flags set the guardrails

Before anything runs, the invocation decides what the run is allowed to do. There is no size-based auto-routing to issues anymore — the default always fixes everything it validates as valid; only --issues-only changes that.

Deterministic
# fix-pr               → resolve PR from current branch
# fix-pr 42            → target PR #42
# fix-pr <url>          → target by URL
fix-pr <pr> --dry-run          # validate + inventory only. NEVER mutates
fix-pr <pr> --issues-only      # file issues for valid findings; never fix
fix-pr <pr> --max-loop=<n>     # override the default 10 fix/review loops
--dry-run is a hard no-mutate promise: no worktree switch, no commits, no pushes, no issues. Reading pinned code via GitHub APIs is fine; touching anything is not.
Default means fix, regardless of size. Finding count, file count, and estimated duration guide how the fix is decomposed into commits — they never route work to issues. Only --issues-only does that.
1

Identify the PR and land on its head-branch worktree

Resolve which PR we're working on, pin its metadata, dispatch feedback collection in parallel, then get onto a git worktree whose checked-out branch is exactly headRefName.

Deterministic Dispatches collectors LLM picks the route

Pin immutable metadata first — the mutation target is headRepository.nameWithOwner:headRefName, not necessarily origin, and headRefOid is the validation anchor for the whole pass:

gh pr view <N> --repo <owner/repo> --json number,title,body,state,url,files,reviews,comments,\
  headRefName,headRefOid,headRepository,headRepositoryOwner,isCrossRepository,baseRefName,baseRefOid
Orchestrate directive: launch two parallel read-only collector tasks now — (1) submitted reviews + conversation comments, (2) inline comments + diff + cited-code anchors — while the mainline finishes worktree selection below. Each returns compact JSON only: { headOid, items: [{ source, id, url, commit, pathLine, claim }] }. A stale headOid or malformed record is rejected; raw PR payloads never leave the collector.

Worktree selection (skipped entirely for --dry-run, which reads pinned code through GitHub APIs instead):

  1. Run git worktree list --porcelain. Git allows one worktree per branch — reuse it if refs/heads/<headRefName> is already checked out somewhere.
  2. Otherwise gh pr checkout <N> --repo <owner/repo> --worktree <absolute-path>. Verify the branch name — a pr-<N> or detached checkout is not the mutation worktree.
  3. If --worktree is unavailable: fetch the head repository, create/reuse a local branch named exactly headRefName, then git worktree add <absolute-path> <headRefName>.
  4. Require the worktree clean, then fetch + fast-forward and confirm both: 
    git -C <worktree> branch --show-current == <headRefName>
git -C <worktree> rev-parse HEAD       == <headRefOid>
    Divergence or a dirty reused worktree is a blocker — preserve the work and report it.

Merge the collector output — review bodies alone are insufficient. Fast path when gh + jq are present:

bash skills/fix-pr/scripts/fetch-feedback.sh <owner/repo> <pr-number>

OMP-preferred: read pr://<N> and read pr://<N>?comments=1. Universal fallback:

gh pr view <N> --repo <owner/repo> --json number,title,body,state,url,files,reviews,comments,headRefName,headRefOid
gh api repos/{owner}/{repo}/pulls/<N>/reviews
gh api repos/{owner}/{repo}/pulls/<N>/comments
gh api repos/{owner}/{repo}/issues/<N>/comments

Diff: full diff via gh pr diff <N> --repo <owner/repo>. For one file, use the worktree or the contents API — not gh pr diff <N> -- <path>:

git -C <worktree> diff <baseRefOid>...<headRefOid> -- <path>
gh api "repos/{owner}/{repo}/contents/<path>?ref=<headRefOid>"
On OMP, prefer read pr://<N>. The procedure never requires OMP — gh always works.

Verified gotcha: gh pr diff accepts at most one positional argument. gh pr diff <N> -- <path> is not a supported path filter; current gh exits with accepts at most 1 arg(s).

2

Inventory every comment into a working table

Turn a messy comment thread into one clean list: who said what, where, at which commit, and where it stands so far.

LLM judgment

Include: review bodies with concrete findings, inline comments and threads, conversation comments requesting changes. Sort and pin: order by submittedAt / createdAt; retain each item's immutable ID, URL, and commit SHA. A later review's silence never supersedes an earlier open finding — only explicit resolution or current-HEAD evidence does.

ClassRule
resolvedSkip unless asked to re-check
nit / LGTM / styleOptional drive-by; never an issue
duplicateSame claim or root cause across all sources → one work item, cite every source incl. earliest submittedAt
staleValid at an earlier reviewed commit, superseded on HEAD → re-validate; mark already_done with evidence, do not re-fix
.context/** onlySkip — except leaked secrets, which are always actionable
Already fixed on HEADalready_done + proof; do not re-fix
Drive-by redesignout_of_scope, or ask if product-ambiguous

Working table — retained across every fix/review loop:

loop | source | id/url | commit | path:line | claim | submittedAt | verdict | disposition
3

Validate every item against the actual code

The heart of the skill: no comment is acted on until the code confirms it. Independent groups validate in parallel; the mainline still makes the call.

Fans out per file / root-cause group Mainline finalizes · evidence required
For every deduplicated pending item or tight root-cause group, dispatch a validator with the pinned headRefOid and its assigned finding IDs. Each validator reads the cited code plus callers/siblings and returns a proposed verdict with concise evidence — never raw payloads. Do not manufacture parallel slices: one remaining group resumes the existing collector via hub send (or the harness equivalent) instead of a padded batch. The mainline accepts or corrects each proposal, records the final verdict, and is the only place a fix, an issue, a mutation, or a settlement decision can originate.
  • Read the cited code and its callers/siblings sharing the root cause.
  • Confirm or disprove with evidence — snippet, test, or runtime output.
  • Root-cause bias: one shared guard beats N call-site patches.
VerdictMeaningNext
validReal bug, missing guard, clear improvementFix by default; issue only under --issues-only
invalidWrong, outdated, or contradicts deliberate designNote why; do not fix
already_doneHEAD already addresses itCite proof
unsureNeeds a product callAsk the engineer
nitStyle onlyOptional / skip

Unsure protocol — one short batched question, not a drip feed:

Comment <N> (@author, path:line):
  Claim: <one sentence>
  Observed: <what code actually does>
  Why unclear: <missing product intent / two reasonable designs>
  Options: (A) …  (B) …
Valid? → fix / issue / skip per your call.
Unresolved unsure items never block unrelated valid fixes.
4

Choose the explicit disposition

A subagent verdict is evidence, not authorization — only the mainline chooses what happens next, and the choice is driven by mode and open-finding state, not size.

LLM judgment Decision gate
Mode / stateAction
--dry-runPhase 6 inventory only — no worktree, fix, issue, commit, push, or poll
--issues-onlyPhase 5b — file every valid finding or tight root-cause group
Valid findings remainPhase 5a — fix all of them, regardless of size
Zero valid; settlement contract already metPhase 6, status settled
Zero valid; no qualifying post-push settlement reviewPhase 5c — poll, using current HEAD + feedback IDs as the anchor
Size changes decomposition, not disposition. A large or risky batch changes commit boundaries, test scope, and how long it takes — never whether it gets fixed. Ask only for genuinely unsure product intent; keep fixing independent valid findings while that answer is pending.
5a

Fix path — smallest correct diff, proven green, pushed to the head branch

Land every valid item with the least change that's provably correct, then hand off to the poll loop.

LLM judgment Deterministic checks
  1. Smallest correct diff for all valid items — shared root cause → one change, not repeated call-site patches.
  2. Regression-protecting tests only, then run the narrowest relevant suite plus every project-required check for touched paths.
  3. Stage the complete verified batch; cross-check the staged diff against the working table — every valid finding maps to a staged change or an explicit blocking decision.
  4. Commit (multiple commits only for independent themes), using the repo's commit skill when present: 
    fix(<scope>): address PR #<N> review (<short theme>)
  5. Confirm the local branch is still exactly headRefName, then push explicitly to the PR head repository and branch (use origin only when it matches headRepository.nameWithOwner; add a remote for a fork PR): 
    git -C <worktree> push -u <head-remote> HEAD:<headRefName>
    Re-fetch PR metadata afterward and require headRefOid to equal local HEAD.
  6. Record the pushed SHA, push time, and every feedback ID already seen, then enter Phase 5c.
The push is a gate: verification green, index staged, commit exists, target is headRefName. An ordinary push only — a rejection is a blocker, not permission to force-push.
5b

Issues path — --issues-only handoff

Runs only under the explicit --issues-only flag. For each valid item or tight root-cause group:

LLM judgment
  1. Search open issues for the same PR and theme — no duplicates.
  2. gh issue create --body-file … with the claim, current-HEAD evidence, paths, acceptance criteria, and PR/comment URLs. Confirm available labels before applying ready-for-agent or needs-triage, plus bug / enhancement as fit.
  3. Record the issue URL in the working table. The path is complete only when every valid finding has a linked issue.
Do not edit, commit, push, or enter the review loop in issues-only mode. Nits never become issues.
5c

Poll for review and repeat until settled

A fix/review loop is one validated fix batch, its verified push, plus the independent review outcome for that push. Default cap 10 loops; --max-loop=<n> overrides it.

Decision gate Fixed poll schedule

After each push, poll at these cumulative intervals — 30 minutes total, never busy-loops:

delay minutes:       2, 2, 2, 2, 2, 5, 5, 10
cumulative minutes:  2, 4, 6, 8, 10, 15, 20, 30

At each poll:

  1. Fetch PR state, headRefOid, submitted reviews, inline comments, thread resolution state, and conversation comments. Compare immutable IDs against the seen-ID set — counts alone are not evidence of new feedback.
  2. Mark new IDs seen and revalidate every new finding against current HEAD, even if it's pinned to an older commit.
  3. New finding is valid:
    • below max-loop → resync the same worktree, restart at Phase 2, fix, verify, commit, push, restart the 30-minute schedule;
    • at max-loop → stop with status max_loops_reached, report every unresolved finding, never convert them to issues implicitly.
  4. No valid finding remains and a different reviewer submitted a post-push review explicitly confirming the issues are resolved, every thread accounted for → finish settled.
  5. Feedback arrived but doesn't settle the PR → continue the remaining intervals. A review introducing new valid findings overrides any contradictory "resolved" wording in that same review.
All eight polls complete with no qualifying settlement review → finish review_pending, never settled. Record the last poll time; resume from Phase 5c on the next invocation without duplicating fixes.
6

Always runs — even after --dry-run, because the diagnosis is worth keeping.

  2. Update .context/memory/index.md.

Non-negotiable behavior rules

These apply across every step and override convenience.

Hard rules
RuleMeaning
Default means fixResolve every valid finding regardless of size; only --issues-only routes to issues
Head-branch worktreeEvery mutation happens in the worktree whose local branch equals headRefName; push to that branch in the head repository
--dry-run is no-mutateGitHub APIs for pinned code; no worktree switch, commit, push, comment, or issue
Validate before mutatingRe-read current HEAD; a resolved label or later review silence is not code-change evidence
Settlement is independentThe PR author never manufactures the review required to declare its own fixes resolved
Bounded waitingPoll at 2,2,2,2,2,5,5,10 minutes and perform at most max-loop fix/review loops
Ask only for unsureValid / invalid / already_done are the agent's job; unresolved unsure never blocks independent fixes
Verification gates the pushRun project-required checks and push only a green fix batch
Secrets stay secretTreat leaks as actionable without copying values into issues or memory
Idempotent resumeKeep feedback IDs and pushed SHAs; revalidate current HEAD, skip already_done, create no duplicate issues
⚠

Error handling

Blockers preserve work and stop; they never silently downgrade to a smaller success.

Stop conditions
SituationResponse
gh missing / unauthenticatedStop; install or authenticate gh
PR not foundStop; ask for URL
Head branch already in another worktreeReuse that absolute worktree path
Reused worktree dirty or branch divergedPreserve it; stop with exact blocker
Checkout fails for another reasonStop; report command and error
Tests fail after fixFix or revert; keep the remote unchanged
Push rejectedStop; preserve commits; no force-push
PR closes or merges during pollingStop mutation and report the remote state
No settlement review after 30 minutesFinish review_pending; never claim settled
Review after loop cap has valid findingsFinish max_loops_reached with exact findings
Cannot create requested issuesSave draft bodies under .context/ and report

Where the model meets the machine

Roughly: the shell fetches, checks out, and pushes; subagents collect and validate in parallel with a slim return contract; the mainline owns every verdict, edit, commit, push, poll, and the settlement call.

gh pr view + fetch-feedback.sh→ parallel collectors→ dedupe + classify inventory→ parallel validators→ mainline verdicts + disposition→ fix, verify, stage→ commit & push to headRefName→ poll up to max-loop→ write memory record
