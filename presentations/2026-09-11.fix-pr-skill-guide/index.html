fix-pr: turn PR review comments into fixed code (or filed issues)

A step-by-step guide to skills/fix-pr/SKILL.md — the skill that reads every comment on a GitHub pull request, checks each one against the actual code, and then either fixes it in the same session or files a tracked issue. It never guesses and it never mutates code it hasn't validated.

Mutates code (when small) Skill-only — no slash command OMP-first, agent-agnostic Asks only when "unsure"

i What is fix-pr, in one paragraph?

Someone reviewed your pull request. Maybe a human, maybe a bot. Now there's a pile of comments — some are real bugs, some are already fixed, some are nitpicks, some are just wrong. fix-pr is the procedure for turning that pile into one of two outcomes: a small, verified commit that addresses everything valid, or a set of well-written GitHub issues for anything too big to do safely right now.

The one rule that matters most Every comment gets checked against the current code before anything happens to it. A reviewer being senior, or a comment sounding confident, is not evidence. Only the code is.

ii When do you reach for it?

Use fix-pr when someone says things like:

"fix the PR comments" "address review feedback" "fix PR #42" points you at a PR URL and wants action, not a report
Not for Just reading/summarizing feedback (that's b-pr-review-2-issues), and not for writing a fresh code review yourself (that's code-review-universal). fix-pr is specifically the "close the loop and mutate something" skill.

iii How it's different from similar-sounding skills

SkillStops atMutates code?
code-review / code-review-universalPosts a reviewNo
b-pr-review-2-issuesPlan artifact in .context/No
fix-prFixed code or filed issuesYes (when small)

fix-pr is the only one of the three that actually touches your repository or opens issues on your behalf.

iv How you invoke it

No slash command exists for this skill on purpose — it's loaded by name (e.g. /skill:fix-pr on OMP) so the full procedure below is always followed, rather than a thin wrapper that might drift out of date.

fix-pr                     # resolve PR from current branch
fix-pr <pr-number>
fix-pr <pr-url>
fix-pr <pr> --issues-only   # never fix code; file issues for valid items
fix-pr <pr> --fix-only      # never file issues; stop if too large to fix
fix-pr <pr> --dry-run       # validate + inventory only; touches nothing
--issues-only

Good for large PRs, or when you want a paper trail before touching code.

--fix-only

Forces a stop (with a report) instead of quietly falling back to filing issues.

--dry-run

Safe to run any time — validates everything, writes a memory note, and stops. No commits, no pushes, no issues.

1 Identify the PR and land on its head branch

Goal: know which PR, and have its full feedback in hand — not just the review summary.

  1. Work out the PR number. If the user gave you one, use it. Otherwise run gh pr view against the current branch. Still nothing? Ask for a URL or number.
  2. Fetch everything — review bodies alone are not enough, because most of the actionable detail lives in inline/file comments and conversation replies.
    On OMP (preferred) 
    read pr://<N>
read pr://<N>?comments=1
    Universal fallback 
    gh pr view <N> --repo <owner/repo> \
  --json number,title,body,headRefName,baseRefName,state,url,files,reviews,comments
gh api repos/{owner}/{repo}/pulls/<N>/comments
gh api repos/{owner}/{repo}/issues/<N>/comments
    Fast path If gh and jq are both installed, one script does all three calls for you and hands back an ordered table — see the script section below.
  3. Get the diff and the code at HEAD — Phase 3 needs both. 
    gh pr diff <N> --repo <owner/repo>                            # full diff
gh api repos/{owner}/{repo}/contents/<path>?ref=<headRefName>    # one file at HEAD
    Known gotcha gh pr diff <N> -- <path> (the path-filtered form) sometimes returns nothing even when that file changed. Use the contents API instead of trusting an empty diff.

2 Inventory every comment into one working table

Goal: one flat list of findings, nothing double-counted, nothing skipped.

What counts as a finding:

  • Submitted review bodies — human and bot — with a concrete claim
  • Inline / file-level review comment threads
  • Conversation comments that request a change

If the PR has several reviews, sort them by submittedAt. The latest review touching a given file/line wins. Tag each finding with the commit SHA of the review it came from — that's how you later spot a comment that a later commit already addressed.

Comment typeRule
Resolved threadsSkip, unless the user explicitly asked to re-check
Nit / LGTM / pure styleOptional drive-by fix; never worth its own issue
Duplicate claimMerge into one work item; cite every source, including the earliest submittedAt
Stale (valid earlier, since fixed)Re-validate against HEAD; mark already_done with evidence — do not re-fix
.context/** onlySkip — session artifacts, not shipped code (except a leaked secret, which is always actionable)
Already fixed on HEADalready_done + evidence; do not touch it again
Out-of-scope redesignout_of_scope, or ask if the product intent is genuinely ambiguous

Every row of the working table looks like this — keep it flat, one row per finding:

# | source | commit | path:line | claim | submittedAt | status: pending_validation

3 Validate each item against the real code

Goal: turn "pending_validation" into a verdict backed by evidence — not vibes.

  1. Read the cited code — and its callers/siblings that share the same root cause. A comment about one call site is often really about a shared helper.
  2. Confirm or disprove with real evidence: a code snippet, a failing test, or an observed runtime behavior.
  3. Classify with one of five verdicts:
VerdictMeaningWhat happens next
validReal bug, missing guard, genuine inconsistency, or clear improvementCounts toward the size gate; gets fixed or turned into an issue
invalidWrong, outdated, or contradicts a deliberate design decision (with evidence)Note why, in one sentence; do not touch the code
already_doneHEAD already addresses itCite the proof (line/commit); move on
unsureNeeds a product or steward call the agent can't make aloneAsk the engineer — see the protocol below
nitStyle-only, no functional stakeOptional drive-by while already editing the file; otherwise skip
Unsure protocol — short and batched, not one question at a time 
Comment <N> (@author, path:line):
  Claim: <one sentence>
  Observed: <what the code actually does>
  Why unclear: <missing product intent / two reasonable designs>
  Options: (A) …  (B) …
Valid? → fix / issue / skip per your call.
Unrelated valid fixes are never blocked waiting on an open unsure — keep moving on everything else.
Root-cause bias If three comments point at the same missing guard in three call sites, that's one fix, not three. Prefer one shared change over N copy-pasted patches.

4 Decide: fix now, or file issues?

Goal: don't start a half-finished branch when the honest answer is "this needs its own session."

Add up every valid finding that's still open (skip anything already_done). Weigh it against these signals:

SignalLean fix nowLean file issues
Valid findings≤ ~5≥ 6, or many unrelated themes
Files touched≤ ~8> 8, or many subsystems
DepthGuard/branch/test tweaks, small UXDesign changes, migrations, multi-layer refactors
RiskLocal, well-tested pathsAuth/payments/data loss, unclear product calls
Time shapeOne focused commit (maybe two)Multi-session, needs product input
Tie-breaker Borderline? File issues. A shippable tracking issue beats a half-finished branch. --fix-only / --issues-only override this judgment call explicitly.
Gate outcomeAction
Fits in-session, no --issues-only→ Phase 5a: Fix
Too large, no --fix-only→ Phase 5b: File issues
--fix-only but too largeStop. Report inventory + a recommended issue split. No partial slog.
Zero valid findingsReport and stop — no commit at all
--dry-run (any count)Stop after Phase 3. Emit the inventory + verdict table only.

5 Execute: fix in-session, or file issues

This phase branches — only one path runs per invocation.

🔧 5a — Fix path

  1. Write the smallest correct diff covering all valid items — one shared root-cause fix beats several call-site patches.
  2. Add or run the narrowest tests that would fail if the fix regressed.
  3. Run those tests, plus any project-required checks for the touched paths.
  4. Commit — one commit is preferred, two max, using: 
    fix(<scope>): address PR #<N> review (<short theme>)
    (use the repo's git-commit skill if present, otherwise a plain conventional commit)
  5. git push -u origin HEAD on the current branch.
  6. Optionally leave a short PR comment summarizing what landed.
  7. Move to Phase 6.
Don't expand into unrelated refactors. Don't push if verification is failing.

🎫 5b — Issues path

  1. Search existing open issues first — don't file a duplicate for the same PR/theme.
  2. For each valid item (or tight theme-group), run: 
    gh issue create --body-file …
    with an actionable title, the claim + evidence, affected paths, acceptance criteria, and links back to the PR + comment URL.
  3. Label ready-for-agent if fully specified, else needs-triage; add bug/enhancement as fits.
  4. Prefer one issue per theme when several comments share a root cause.
  5. Leave a short PR comment listing the filed issues.
  6. Don't implement anything here — unless exactly one trivial valid item remains and --issues-only wasn't set.
Never file issues for nits. Pure style comments get a drive-by fix or get skipped from the report — they never earn a tracked issue.

6 Write the durable record and close out

Goal: anyone (including future-you) can see exactly what happened without re-reading the PR.

  1. Write .context/memory/fix-pr-<pr>-YYYY-MM-DD.md (or the active subject folder) containing: the PR URL/number, the full validation table with a verdict per comment, fix SHAs or issue URLs, and every command run plus its result.
  2. Update .context/memory/index.md so the session is discoverable later.
  3. Report a closeout in this exact shape: 
    PR #<N> — <title>
Branch: <head> (pushed: yes/no)

Validation:
| # | claim | verdict | disposition |
|---|---|---|---|
| 1 | … | valid | fixed in <sha> |
| 2 | … | invalid | <reason> |
| 3 | … | unsure | asked → <decision> |
| 4 | … | valid | issue #M |

Verification:
- <command> → <result>

Follow-ups: <none | issue links>
This step runs even under --dry-run — the diagnosis is worth keeping even though nothing was pushed or filed.

★ Golden rules — the things that never bend

  • --dry-run never mutates. Reading code on the PR's head branch is fine; committing, pushing, or opening issues is not.
  • Validate before mutating. No drive-by "fixes" for a comment you haven't checked.
  • Evidence over deference. A senior reviewer's confidence doesn't make a wrong comment right.
  • Only ask for "unsure". Valid, invalid, and already_done are calls the agent makes itself.
  • No plan-only theater. Small enough to fix? Fix it. Too big to plan safely in-session? Hand off to b-pr-review-2-issues or b-plan instead of misusing this skill.
  • Stay on the correct branch. Never fix on the wrong checkout.
  • Verify narrowly — unless the project's own rules demand more.
  • Secrets are always actionable — and never get copied into an issue or memory file.
  • Bot noise doesn't count. "CI still running" isn't a finding; a concrete bot-reported bug is.
  • Idempotent re-runs. Re-validate everything, skip what's already_done, never file the same issue twice.

! When something goes wrong

SituationWhat to do
gh missing or unauthenticatedStop; install it or run gh auth login
PR not foundStop; ask for a URL
Checkout failsStop; report why
Tests fail after the fixFix it or revert — never push red
Push rejectedReport it; never force-push unless explicitly told to
Can't create issuesReport the valid items and save draft bodies under .context/ instead

›_ The fast path: fetch-feedback.sh

One script, three gh calls, one ordered table — used at the start of Phase 1/2.

Instead of running three separate gh commands and manually stitching the results together, this script does it for you — if both gh and jq are on your PATH. If either is missing, it fails loudly and you fall back to the raw gh commands documented in Phase 1. 

bash skills/fix-pr/scripts/fetch-feedback.sh <owner/repo> <pr-number>

What it does, step by step:

  1. Checks that gh and jq both exist — exits with a clear message if not.
  2. Calls three GitHub endpoints: the PR itself (gh pr view), inline review comments (pulls/<N>/comments), and conversation comments (issues/<N>/comments).
  3. Confirms the PR actually exists — GitHub returns an empty object for unknown PRs instead of an error, so the script checks .number explicitly.
  4. Emits one tab-separated table, sorted so reviews come first (by submittedAt), then inline comments, then conversation comments — each row tagged with its source.

Output shape (header + one row per finding):

#	source	commit	path:line	claim	submittedAt	status
	review		src/foo.ts	Missing null check before…	2026-09-01T12:00:00Z	pending_validation
	inline	1a7a6aa	src/foo.ts:42	Should this throw instead of…	2026-09-01T13:04:00Z	pending_validation
	conversation			Can we also cover the empty-…	2026-09-01T14:10:00Z	pending_validation
What it deliberately does not do No semantic deduplication, no classification (it never decides valid vs already_done vs stale). That judgment stays with the agent in Phases 2–3 — the script only fetches, orders, and tags. If that classification logic ever becomes fully mechanical, it belongs in the script; until then, it stays a human/agent call.
Commit SHA is best-effort Review bodies sometimes contain a line like Commit: 1a7a6aa, which the script extracts via regex. When it's absent, the SHA column is just empty — the real staleness signal is the submittedAt ordering, not the SHA.
