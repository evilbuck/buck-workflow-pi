# b-triage: Inbound Issue Triage

Move an issue (or, when configured, an external PR) on this repo's issue
tracker through a small state machine of triage roles. The only missing
**inbound** stage in this repo's skill set — every other issue-facing skill
(`b-issue-create`, `b-pr`, `fix-pr`, `b-pr-review-2-issues`) points outward.

> Origin: ported from `mattpocock/skills` (`skills/engineering/triage/`, MIT). See `THIRD-PARTY-NOTICES.md` at the repo root.

Reads its tracker and label configuration from `docs/agents/issue-tracker.md`
and `docs/agents/triage-labels.md`. If either is missing, tell the user to
run `/b-init-tracker` first.

If this repo's `issue-tracker.md` has "PRs as a request surface: yes",
triage covers external PRs too: **a PR is an issue with attached code**,
same roles, same states, same machine, with the deltas marked "for a PR"
below.

Every comment posted to the tracker during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable, behavioural agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `.out-of-scope/` knowledge base works

## Roles

Two **category** roles: `bug` (something is broken), `enhancement` (new
feature or improvement).

Five **state** roles (canonical names — map to this repo's actual label
strings via `docs/agents/triage-labels.md`):

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent — this is the
  state `b-auto-fix` consumes as its input
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

For a PR, the same states read against the attached code:
`ready-for-agent` means a brief is attached and an agent should take the
next step on the diff; `ready-for-human` means it's ready for a human to
merge.

Every triaged issue carries exactly one category role and one state role.
If state roles conflict, flag it and ask the maintainer before doing
anything else.

## Invocation

The maintainer invokes `/b-triage` and describes what they want in natural
language:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the tracker (via `docs/agents/issue-tracker.md`'s CLI conventions)
and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**:
   needs re-evaluation.

When PRs are in scope, include external PRs and tag each line `[PR]` or
`[issue]`. Discovery surfaces only *external* PRs — an explicitly named PR
is always triaged regardless of author.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue/PR (body, comments, labels,
   author, dates; diff too for a PR). Parse prior triage notes so you don't
   re-ask resolved questions. Explore the codebase using its domain
   glossary (`CONTEXT.md`), respecting ADRs in the area. Run two checks:
   - **Redundancy**: search for an existing implementation of the
     requested behavior by domain concept, not just the request's wording.
     Report where you looked. If found, it's an already-implemented
     `wontfix` (step 5).
   - **Prior rejection**: read `.out-of-scope/*.md` and surface any
     concept resembling this request.
2. **Recommend.** Tell the maintainer your category/state recommendation
   with reasoning, plus a brief codebase summary. Wait for direction.
3. **Verify the claim.** Before any grilling, check that the claim holds
   up. For a bug, reproduce it (link to `b-diagnose` if it's genuinely
   hard). For a PR, check it out and run the relevant tests or commands.
   Report: confirmed (with code path), failed, or insufficient detail (a
   strong `needs-info` signal).

   **Gate: an unverified claim is not triaged.** A failed or
   not-yet-performed verification blocks `ready-for-agent` and blocks
   writing an agent brief — route to `needs-info` (failed or
   insufficient-detail) or keep gathering context instead. The maintainer
   may explicitly override via the quick state override below; absent
   that, do not skip this gate.
4. **Grill (if needed).** If the request needs fleshing out, load
   `b-grill` (or `b-grill-with-docs` if domain docs exist) a round of
   questions at a time, sharpening domain terms and updating `CONTEXT.md`
   / ADRs inline as decisions land.
5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: same structure as an agent brief, noting why it
     can't be delegated (judgment calls, external access, design
     decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - `wontfix`: close, comment depends on *why*:
     - **Already implemented**: point to where it lives; do **not** write
       to `.out-of-scope/` (that KB is for *rejected* requests, not built
       ones).
     - **Rejected (bug)**: polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link from a
       comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role; optional comment if there's partial
     progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply
the role directly. Confirm what you're about to do, then act. Skip
grilling. If moving to `ready-for-agent` without a grilling session, ask
whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so
the work isn't lost. Questions must be specific and actionable.

## Resuming a previous session

If prior triage notes exist, read them, check whether the reporter has
answered outstanding questions, and present an updated picture before
continuing. Don't re-ask resolved questions.
